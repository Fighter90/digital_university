# Безопасность простыми словами

Задание жюри: «каждый студент видит только свои данные, пароли не хранятся в
открытом виде, ключи не лежат в коде». Как это устроено у нас:

## 1. Студент видит только свои данные (защита от IDOR)

- Всё чтение идёт через сервер (React Server Components / server actions) —
  браузер не получает чужие данные, чтобы «спрятать» их на клиенте.
- Каждый запрос фильтруется по владельцу сессии: `prisma.request.findMany({
  where: { studentId: session.user.studentId } })`. Подставить в адрес чужой id
  бессмысленно — фильтр не по адресу, а по сессии.
- Автотесты: для каждой сущности есть тест «студент A не видит объект студента B».
- Кабинет сотрудника — отдельная роль; действия сотрудников логируются.

## 2. Пароли не в открытом виде

- Хэш bcrypt (cost 10+). В БД хранится только хэш.
- Вход ограничен rate-limit'ом (защита от перебора), сессии — httpOnly cookie.
- Тестовые аккаунты жюри — вымышленные, пароли одноразовые, опубликованы в
  комментарии к работе (не в коде).

## 3. Ключи не в коде

- `.env` в `.gitignore`; в репозитории только `.env.example` без значений.
- Ключи TimeWeb/Linear/Figma — переменные окружения рабочей машины.
- В браузер пользователя секреты не попадают: серверные переменные читаются
  только на сервере (без префикса `NEXT_PUBLIC_`).

## 4. Прочее

- Заголовки безопасности Next (CSP, X-Frame-Options) не ослабляются — это
  пункт чек-листа security-агента роя.
- Все данные прототипа вымышленные; реальные ПДн запрещены правилами роя
  (`AGENTS.md`) и проверяются отдельным агентом в каждом PR.
