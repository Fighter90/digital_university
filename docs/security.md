# Безопасность простыми словами

Задание жюри: «каждый студент видит только свои данные, пароли не хранятся в
открытом виде, ключи не лежат в коде». Как это устроено у нас:

## Как устроен вход

Студент входит по логину и паролю, и проверяет их только наш сервер. Сам пароль
мы не храним нигде: в базе лежит лишь его необратимый «слепок» (современный
алгоритм argon2id), поэтому даже тот, кто увидит базу, пароль не узнает. После
успешного входа сервер выдаёт браузеру «пропуск» — длинную случайную строку в
защищённой cookie, недоступной скриптам страницы, а в базе хранит только
контрольную сумму пропуска. Пропуск действует 7 дней и автоматически
продлевается, пока человек пользуется кабинетом: вместе с записью в базе
продлевается и сама cookie (раунд ревью 3), так что активный пользователь не
разлогинивается. Кнопка «Выйти со всех устройств» отменяет сразу все его
пропуска. Пять неверных попыток подряд блокируют вход на 15 минут, слишком
частые попытки с одного адреса отсекаются лимитом, и сообщение об ошибке
всегда одинаковое — перебор паролей не имеет смысла. Сотрудники деканата
работают в отдельном разделе с отдельной ролью, и студент не попадёт туда даже
вручную через адресную строку.

## 1. Студент видит только свои данные (защита от IDOR)

- Всё чтение идёт через сервер (React Server Components / server actions) —
  браузер не получает чужие данные, чтобы «спрятать» их на клиенте.
- **Изоляция — архитектурная, а не дисциплина экранов (DIG-12)**: страницы,
  роуты и действия могут читать данные только через функции
  `src/server/data/*`, и каждая функция принимает контекст сессии
  (`DataCtx`), в котором уже лежит владелец (studentId), своя группа и
  факультет. URL в контекст не попадает никогда — фильтр не по адресу, а по
  сессии; прямой импорт Prisma вне `src/server/` запрещён правилом ESLint и
  закреплён тестами.
- Заявки в URL адресуются не порядковым id, а публичным номером
  `SR-2026-A1B2C` со случайным суффиксом — пронумеровать чужие заявки
  перебором нельзя, и даже угаданный номер бесполезен: доступ по одному
  объекту перепроверяет владельца внутри слоя данных.
- **Чужой объект и несуществующий объект выглядят одинаково**: оба дают
  одну и ту же страницу 404 (для API — один и тот же JSON) — ответы нельзя
  использовать как «детектор существования» чужих данных. Различие
  фиксируется только в журнале аудита: каждая попытка открыть чужое
  записывается с причиной (чужое / не найдено / не та роль / чужой
  факультет).
- Кабинет сотрудника — отдельная роль; сотрудник видит только студентов
  своего факультета, и его действия тоже логируются.
- Автотесты: на каждую функцию слоя есть тест «студент A не видит объект
  студента B» + e2e «Анна открывает заявку Ильи → 404» (страница и API).

## 2. Пароли не в открытом виде

- Хэш **argon2id** (memory 19 MiB, iterations 2, parallelism 1 — рекомендации
  OWASP; библиотека `@node-rs/argon2`). В БД хранится только хэш, открытые
  пароли не хранятся и не логируются (DIG-11).
- Сессии: случайный токен 256 бит в cookie `__Host-session` (HttpOnly, Secure,
  SameSite=Lax); в БД — только SHA-256 токена. Скользящее продление (раунд
  ревью 3) работает по обе стороны: хранилище продлевает запись, а middleware
  пере-выдаёт cookie активному браузеру с тем же значением и полным сроком —
  без этого cookie умирала через 7 дней после входа, как бы активен человек
  ни был. Вход ограничен: 5 неудачных попыток → блокировка на 15 минут +
  rate limit по IP (DIG-11).
- Rate limit по IP (раунд ревью 2): адрес берётся из `X-Real-IP`, который
  ставит наш обратный прокси (контракт Caddy: `header_up X-Real-IP
  {remote_host}`), а без него — из последнего элемента `X-Forwarded-For`.
  Первый элемент этого заголовка контролирует сам клиент, поэтому он не
  считается доверенным: подменяя его, нельзя получить новый лимит.
- Сообщение «Слишком много попыток, попробуйте через 15 минут» выдаётся только
  для существующего логина и тем самым раскрывает, что он существует, —
  осознанный компромисс: пользователю честнее назвать время разблокировки,
  а перечисление логинов ограничено теми же 5 попытками и блокировкой.
- Тестовые аккаунты жюри — вымышленные, пароли одноразовые, опубликованы в
  комментарии к работе (не в коде).

## 3. Ключи не в коде

- `.env` в `.gitignore`; в репозитории только `.env.example` без значений.
- Ключи TimeWeb/Linear/Figma — переменные окружения рабочей машины.
- В браузер пользователя секреты не попадают: серверные переменные читаются
  только на сервере (без префикса `NEXT_PUBLIC_`).

## 4. Прочее

- Мутационные API-роуты (`/api/*`, всё кроме GET/HEAD) проверяют Origin
  (раунд ревью 2): чужой Origin и запрос **без** Origin (curl,
  межсерверный вызов) отклоняются с 403 — fail-closed. Браузеры всегда
  присылают Origin на POST, так что легитимное использование из кабинета
  не ломается. Пока мутационных API-роутов в прототипе нет, поведение
  закреплено тестами на будущее.
- Заголовки безопасности Next (CSP, X-Frame-Options) не ослабляются — это
  пункт чек-листа security-агента роя.
- Все данные прототипа вымышленные; реальные ПДн запрещены правилами роя
  (`AGENTS.md`) и проверяются отдельным агентом в каждом PR.
