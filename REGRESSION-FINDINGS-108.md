## DIG-108: MCP-сервер

### Прода, негативные проверки (curl)

- `POST /api/mcp` без `Authorization` → `HTTP 401`, JSON-RPC-ошибка `-32001`,
  `WWW-Authenticate: Bearer realm="digital-deanery-mcp"` — байт-в-байт как в
  `docs/mcp.md` («Живой ответ прода», проверено 2026-11-19).
- С мусорным токеном → `HTTP 401`, `-32001`,
  `WWW-Authenticate: Bearer realm="digital-deanery-mcp", error="invalid_token"`.
- Лог: `mcp-prod-negative.log`.

### Полный сеанс с токеном (локально, локальная БД)

Токен выпущен штатным путём: вход `anna.smirnova` → «Настройки → Настройка MCP»
→ «Выпустить токен» (server action `generateMcpDemoToken` + `rotateOwnMcpToken`;
в хранилище — только SHA-256). Плейнтекст жил только в локальном untracked-файле
для curl-прогона и удалён сразу после него; в логах — только хэш.

Последовательность `initialize → notifications/initialized → tools/list →
tools/call ×3 → ping` (Playwright + curl, транскрипт `mcp-smoke-local.log`):

## Дефекты

### D1 (глобальный, не исправлялся): заявки мастера невидимы сотруднику

**Симптом.** Заявка, поданная студентом через мастер `/requests` (канонические
заявки DIG-30, номера ЗД-…), не появляется в очереди `/staff/requests` и её
карточка `/staff/requests/ЗД-…` отдаёт 404. В очереди — только легаси-заявки
(ЗС/SR-…). Подтверждено на проде: ЗД-2026-000010 отсутствует в очереди
(скриншот 110-10), при этом легаси-строка берётся в работу штатно.

**Причина (по коду).** Слои не стыкованы:

- мастер создаёт строки через `createCanonicalRequest` → `insertCanonicalRequest`
  (таблица канона, `src/server/data/canonical-requests.ts`);
- кабинет сотрудника читает только легаси: `getStaffQueue` →
  `db.listRequestsByFaculty` (memory-адаптер фильтрует массив `requests`,
  канон не смотрит), карточка — `probeRequestByNumber` (тоже только легаси),
  переходы — `updateRequestByStaff` (легаси);
- в `src/app/(cabinet)/staff/**` нет ни одного упоминания canonical.

**Влияние.** Разорван основной продуктовый обещанный контур «студент подал →
сотрудник взял в работу → студент видит статус» для всего нового потока заявок
(справки, академический отпуск, матпомощь…). Студентский контур работает, но
заявка «зависает» в статусе «Подана»/«Готова» без участия деканата.

**Почему не фикшено в рамках регресса.** Минимальной правки нет: нужна
интеграция слоёв — порт `listCanonicalRequestsByFaculty`, скоупленые staff-
переходы канона (сейчас `saveCanonicalRequestStatus` не проверяет факультет
сотрудника), очередь/карточка/действия для ЗД-номеров, SLA-политика для
`CanonicalRequestRow` (`etaDays` типа). Это фичеработ уровня отдельной задачи
(DIG-48 ↔ DIG-30 integration), не «минимальный фикс регресса». Рекомендация:
завести отдельную Linear-задачу «Канонические заявки в кабинете сотрудника».

### D2 (исправлен, минимальный фикс + тест): `export type` в `'use server'` роняет dev-режим

**Симптом.** `next dev` (Turbopack): страницы, в bundles которых попадает
`src/server/actions/floating-assistant.ts`, отвечали 500 —
`ReferenceError: FloatingAssistantReply is not defined` на
`export type { FloatingAssistantReply };` (строка 18). Прод-сборка не задета
(типы стираются при build), поэтому дефект жил только в dev.

**Фикс.** Удалён реэкспорт типа из `'use server'`-модуля
(`src/server/actions/floating-assistant.ts`); единственный потребитель
(`src/components/assistant/floating-assistant-popup.tsx`) импортировал тип из
actions-файла — тип теперь берёт напрямую из `@/server/ai/floating-assistant`
(runtime-импорт action не изменился). Контракт наружу не менялся.

**Тест (red-first).** `tests/actions-no-type-exports.test.ts` — статический
контракт: в `src/server/actions/*.ts` запрещены реэкспорты вида
`export type { T };` (объявления-алиасы `export type X = …` разрешены — они в
dev работают). До фикса тест падал на `floating-assistant.ts:18`, после —
зелёный.

**Замечание к ревью (не дефект).** Клиентские `<Link>`/redirect-навигации на
проде изредка гоняются с revalidate-ре-рендером (ссылка отсоединяется во время
клика); e2e-сценарии это знают (`catch` + прямые переходы). Продуктового бага
не зафиксировано — для надёжности можно рассмотреть `redirect()` вместо
`router.refresh()`-паттернов на submit-экранах, но это опционально.
