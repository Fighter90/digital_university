# auth Specification

## Purpose
Вход по логину/паролю, сессии и их куки, защита от перебора, выбор хранилища, выход безвозвратно — единый периметр аутентификации и доступа.
## Requirements
### Requirement: Вход по логину и паролю

Требование «Вход по логину и паролю» — обязательное (MUST): Пароли проверяет только сервер; хранится exclusively argon2id-хэш
(19 MiB / 2 / 1). Открытые пароли нигде не сохраняются и не логируются.

#### Scenario: Успешный вход

- **WHEN** студент вводит верные логин и пароль
- **THEN** сервер создаёт сессию, кладёт в cookie `__Host-session` случайный
  токен 256 бит и возвращает пользователя (id, login, role)

#### Scenario: Единая ошибка без подсказки

- **WHEN** введён неверный пароль ИЛИ несуществующий логин
- **THEN** возвращается одинаковый текст «Неверный логин или пароль.»,
  и проверка по времени не отличает эти два случая

### Requirement: Сессии

Cookie `__Host-session` (HttpOnly, Secure, SameSite=Lax, Path=/) ДОЛЖНА (MUST)
хранить токен сессии (в БД — только его SHA-256), жить 7 дней со скользящим
продлением — и в хранилище (resolveSession), и в самих cookie.
Middleware ОБЯЗАН (MUST) пере-выдавать обе авторизационные куки
(`__Host-session` и `__Host-role`) с прежними значениями и полным
Max-Age на каждом разрешённом запросе, который является чтением
(GET/HEAD) и НЕ является speculative prefetch'ем роутера
(`Next-Router-Prefetch: 1`); мутационные запросы (POST/PUT/DELETE/
PATCH — включая server actions, в том числе sign-out) куки не
пере-выдают. Значения кук в middleware никогда не меняются (новых
токенов и полномочий не создаётся); prefetch-ответ может примениться
браузером в произвольный момент — в том числе ПОСЛЕ куки-очистки
sign-out action'а — поэтому он не имеет права писать auth-куки
(регресс e2e `auth.spec` «Выйти не удаляет куку __Host-session»).

#### Scenario: Истечение сессии

- **WHEN** срок сессии истёк и пользователь открывает защищённую страницу
- **THEN** сессия не резолвится, посетитель уходит на `/login?next=…`

#### Scenario: Скользящее продление живой сессии на навигации

- **WHEN** браузер с живой сессией выполняет GET/HEAD-переход по
  разрешённой странице без заголовка `Next-Router-Prefetch: 1`
- **THEN** ответ пере-выдаёт `__Host-session` (и `__Host-role`) с теми же
  значениями и полным `Max-Age=604800`; срок в хранилище продлевается
  до полных 7 дней (контракт review round 3 DIG-55 сохранён)

#### Scenario: Prefetch защищённого пути не продлевает куки

- **WHEN** GET-запрос на защищённый путь несёт валидную куку
  `__Host-session` и заголовки `RSC: 1`, `Next-Router-Prefetch: 1`
- **THEN** ответ имеет статус 200 и НЕ содержит `Set-Cookie` ни для
  `__Host-session`, ни для `__Host-role`

#### Scenario: Prefetch публичного пути не продлевает куки

- **WHEN** GET-запрос на публичный путь (например, `/login`) несёт куку
  `__Host-session` и заголовок `Next-Router-Prefetch: 1`
- **THEN** ответ НЕ содержит `Set-Cookie` для auth-кук

#### Scenario: Настоящая RSC-навигация продлевает куку по-прежнему

- **WHEN** GET-запрос несёт куку `__Host-session` и `RSC: 1` БЕЗ
  `Next-Router-Prefetch: 1`
- **THEN** ответ переиздаёт `__Host-session` с тем же значением токена и
  полным `Max-Age=604800`

#### Scenario: Мутация (server action) не продлевает куки

- **WHEN** браузер с живой `__Host-session` отправляет POST server action
- **THEN** middleware ответ не пере-выдаёт (никаких Set-Cookie
  авторизационных кук), чтобы не конкурировать с куки-очисткой action'а

#### Scenario: Клиент без роутерных заголовков продлевает как прежде

- **WHEN** обычный HTTP-клиент (curl, старый браузер) выполняет GET по
  разрешённому пути с валидной кукой и без `Next-Router-Prefetch: 1`
- **THEN** куки продлеваются — признак prefetch единственный и
  детерминированный (никакой эвристики по Fetch-Metadata нет)

### Requirement: Защита от перебора

Требование «Защита от перебора» — обязательное (MUST):

#### Scenario: Блокировка после 5 неудач

- **WHEN** подряд 5 раз введён неверный пароль
- **THEN** аккаунт блокируется на 15 минут; даже верный пароль отклоняется,
  сообщение «Слишком много попыток, попробуйте через 15 минут.»

#### Scenario: Снятие блокировки

- **WHEN** 15 минут истекли
- **THEN** счётчик неудач начинается заново, верный пароль работает

#### Scenario: Rate limit по IP

- **WHEN** с одного IP за 15 минут поступает более 30 попыток входа
- **THEN** попытки отклоняются до проверки пароля, у другого IP лимит свой

#### Scenario: Подмена IP-заголовка (раунд ревью 2)

- **WHEN** клиент шлёт поддельный первый элемент `X-Forwarded-For`
- **THEN** лимит считается по `X-Real-IP`, проставленному обратным прокси
  (контракт Caddy: `header_up X-Real-IP {remote_host}`), а без него — по
  последнему hop `X-Forwarded-For`; клиентский первый элемент не является
  доверенным и «свежий» лимит подменой не получить

### Requirement: Маршруты и роли

Требование «Маршруты и роли» — обязательное (MUST): Middleware не пускает неавторизованных в кабинет и студентов в `/staff`;
Server Actions защищены от CSRF средой Next.js, мутационные API-роуты —
проверкой Origin в middleware.

#### Scenario: Неавторизованный в кабинет

- **WHEN** без сессии открыть `/dashboard`
- **THEN** redirect на `/login?next=%2Fdashboard`; `next` принимает только
  пути внутри приложения (защита от open redirect)

#### Scenario: Студент в /staff

- **WHEN** авторизованный студент открывает `/staff`
- **THEN** redirect на `/dashboard`; каждый staff-экран перепроверяет роль
  на сервере через `requireStaff()`

#### Scenario: Активный сотрудник не теряет /staff (раунд ревью 3)

- **WHEN** сотрудник продолжает пользоваться кабинетом, и подписанный
  hint `__Host-role` подходит к своему 7-дневному сроку
- **THEN** middleware пере-выдаёт hint вместе с session-cookie (то же
  значение, полный Max-Age) на каждом разрешённом запросе; при redirect-е,
  отказе CSRF и непроверяемой подписи cookie не продлевается — раньше hint
  истекал через 7 дней после входа, и сотрудник терял middleware-пропуск
  в `/staff` до повторного входа

#### Scenario: Чужой Origin у API-мутации

- **WHEN** POST на `/api/*` с Origin другого сайта
- **THEN** ответ 403; GET-запросы не проверяются

#### Scenario: Мутация без Origin (раунд ревью 2)

- **WHEN** POST на `/api/*` без заголовка Origin (curl, межсерверный вызов)
- **THEN** ответ 403 — проверка работает по принципу fail-closed: браузеры
  всегда присылают Origin на POST, поэтому легитимное использование из
  веб-интерфейса не ломается, а «спрятать» запрос отсутствием Origin нельзя

### Requirement: Демонстрация Госуслуг

Требование «Демонстрация Госуслуг» — обязательное (MUST):

#### Scenario: Кнопка Госуслуг неактивна

- **WHEN** пользователь видит форму входа
- **THEN** кнопка «Войти через Госуслуги» неактивна и помечена «демо»,
  реальной интеграции нет

### Requirement: Выбор auth-хранилища по DATABASE_URL

Приложение ДОЛЖНО (MUST) выбирать auth-store по единственному признаку —
наличию непустого `process.env.DATABASE_URL`: задан → prisma-store
(generated client `@/generated/prisma` + драйвер-адаптер
`@prisma/adapter-pg`); не задан → memory-store. Откат на memory при
заданном `DATABASE_URL` ЗАПРЕЩЁН: недоступность PostgreSQL проявляется
ошибкой на конкретном запросе (fail loud), а не молчаливой деградацией
в память. Запуск на memory-store без `DATABASE_URL` ДОЛЖЕН (MUST)
логировать WARN с именем переменной и последствием (сессии и
пользователи живут в памяти процесса).

#### Scenario: задан DATABASE_URL — Prisma без отката в память

- **WHEN** приложение стартует с непустым `DATABASE_URL` и PostgreSQL
  недоступен
- **THEN** запросы падают ошибкой подключения (fail loud); молчаливого
  переключения на memory-store не происходит

#### Scenario: не задан DATABASE_URL — memory-store с WARN

- **WHEN** приложение стартует без `DATABASE_URL`
- **THEN** используется memory-store, в логах WARN с именем переменной и
  последствием (сессии/пользователи в памяти процесса)

### Requirement: Сессия без владельца трактуется как отсутствующая

Адаптер сессии Prisma ДОЛЖЕН (MUST) запрашивать владельца вместе с
сессией (`include: { user: true }`); сессия без строки-владельца
трактуется как отсутствующая (fail closed), а не как ошибка запроса
(уточнение контракта DIG-11).

#### Scenario: осиротевшая сессия не резолвится

- **WHEN** `findSessionByTokenHash` находит строку сессии, чей владелец
  удалён из БД
- **THEN** результат — «сессия отсутствует» (посетитель уходит на
  `/login?next=…`), ошибки запроса нет

### Requirement: Выход завершает сессию безвозвратно

Кнопка «Выйти» ДОЛЖНА (MUST) вызывать server action `signOutAction`,
удаляющий сессию в хранилище; «Выйти на всех устройствах» ДОЛЖНА (MUST)
вызывать `signOutAllDevicesAction`, отзывающий все сессии пользователя,
и
выставляют ОБЕ куки в сбрасывающее состояние (`buildClearedSessionCookie()`/
`buildClearedRoleHintCookie()`: `value: ''`, `maxAge: 0`, `path: '/'`,
атрибуты HttpOnly/Secure/SameSite совпадают с выдачей, Domain
отсутствует). Middleware не пере-выдаёт куки на мутациях, поэтому
куки-очистка action'а единолично определяет состояние браузера после
выхода. Проверка отсутствия обеих кук на `/login?signedOut=1` —
обязательная часть e2e-приёмки, включая состояние после «Назад» и при
выполнении prefetch-трафика, ушедшего до клика.

#### Scenario: «Выйти» в меню аватара удаляет сессию и куки

- **WHEN** авторизованный пользователь нажимает «Выйти» в меню аватара
- **THEN** server action удаляет сессию в хранилище, в ответе очищаются
  `__Host-session` и `__Host-role` (`Max-Age=0`), и браузер после ответа
  этих кук не имеет

#### Scenario: «Выйти на всех устройствах» из настроек

- **WHEN** авторизованный пользователь в «Настройки → Безопасность»
  нажимает «Выйти на всех устройствах»
- **THEN** `signOutAllDevicesAction` отзывает все сессии пользователя и
  очищает обе куки; браузер на `/login?signedOut=1` не имеет ни
  `__Host-session`, ни `__Host-role`

#### Scenario: E2E-контракт выхода

- **WHEN** пользователь нажал «Выйти» и оказался на `/login?signedOut=1`
- **THEN** куки `__Host-session` и `__Host-role` в браузере отсутствуют —
  независимо от prefetch-трафика, ушедшего до клика

#### Scenario: Middleware не воскрешает куку на server action

- **WHEN** браузер с живой `__Host-session` отправляет POST server action
- **THEN** middleware ответ не пере-выставляет (никаких Set-Cookie
  авторизационных кук), чтобы очистка из ответа action'а оставалась
  последним словом

#### Scenario: После «Назад» куки не воскресают

- **WHEN** после успешного выхода пользователь возвращается «Назад» на
  защищённый экран
- **THEN** экран отдаётся с `Cache-Control: no-store`, middleware без
  сессии отдаёт редирект на `/login?next=…`, и в браузере по-прежнему
  нет ни одной куки `__Host-*`

### Requirement: Подтверждение выхода на экране входа

Требование «Подтверждение выхода на экране входа» — обязательное (MUST): После выхода пользователь попадает на `/login?signedOut=1`, где экран входа
показывает вежливое `role="status"`-сообщение об успешном выходе.

#### Scenario: Сообщение об успешном выходе

- **WHEN** выполнен выход (любым из двух actions) и открыт `/login?signedOut=1`
- **THEN** страница входа показывает статус «Вы вышли из кабинета…»
  (`role="status"`)

#### Scenario: Без параметра сообщения нет

- **WHEN** открыт обычный `/login` без `?signedOut=1`
- **THEN** сообщение об успехе не рендерится

### Requirement: Вход после выхода

Требование «Вход после выхода» — обязательное (MUST):

#### Scenario: Вход с /login?signedOut=1 завершается ошибкой
- **WHEN** вход с /login?signedOut=1 завершается ошибкой
- **THEN** параметр signedOut убирается из адресной строки (без перезагрузки страницы) и устаревший статус «Вы вышли из кабинета» скрывается — вместе с ошибкой не показывается ни одного противоречащего сообщения.
