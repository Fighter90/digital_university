# people Specification

## Purpose
Справочник преподавателей и сотрудников: поиск по словоформам/email/телефону, избранное, персонализация из скоупа сессии.
## Requirements
### Requirement: Поиск по справочнику

Справочник `/people` ДОЛЖЕН (MUST) искать по ФИО, должности, подразделению и
дисциплинам без учёта регистра и лишних пробелов. Совпадения в ФИО ДОЛЖНЫ
подсветиться `<mark>`. Пустой запрос показывает весь список; если ничего
не нашлось — состояние «Никого не нашлось» с подсказкой сбросить запрос
или фильтр.

#### Scenario: поиск по дисциплине

- **WHEN** Анна вводит в поиск «базы»
- **THEN** остаётся карточка Соколова (ведёт «Базы данных»), совпадение
  в ФИО других карточек не подсвечено, при вводе «хюргв» — пустое
  состояние «Никого не нашлось».

#### Scenario: подсветка совпадения

- **WHEN** Анна вводит «петров»
- **THEN** в ФИО совпавших карточек вхождение обёрнуто в `<mark>`
  (регистр исходного текста сохранён).

### Requirement: Быстрые фильтры

Справочник ДОЛЖЕН (MUST) иметь фильтры-пилюли «Мои преподаватели», «Мой
деканат», «Все» (по умолчанию). «Мои преподаватели» — преподаватели из
расписания и дисциплин группы студента; «Мой деканат» — сотрудники
деканата факультета студента. Фильтр работает совместно с поиском (AND).
У сотрудника деканата персональные фильтры не дают персональных выборок.

#### Scenario: фильтр «Мои преподаватели»

- **WHEN** Анна (ПИ-21, ИТ) включает фильтр «Мои преподаватели»
- **THEN** остаются только преподаватели её группы (Петров, Иванова,
  Соколов, Орлов, Кузнецова), а при «базы» в поиске — только Соколов.

#### Scenario: фильтр «Мой деканат»

- **WHEN** Анна включает фильтр «Мой деканат»
- **THEN** остаются только сотрудники деканата факультета ИТ; сотрудники
  деканата ЭК и общих служб скрыты.

### Requirement: Карточка в списке

Карточка ДОЛЖНА (MUST) показывать аватар-инициалы, ФИО (ссылка на
`/people/<id>`), должность, подразделение и дисциплины студента у этого
преподавателя («Ваши дисциплины: …»). У менеджера программы студента —
плашка «Ваш менеджер» прямо в списке. Записи с персональными связями
сортируются поверх, далее — по алфавиту ФИО (сортировка стабильна,
ревью DIG-37 r5: точный набор и порядок «Моих преподавателей»
проверяется e2e). На 360 px — одна колонка, от 640 px — две.

#### Scenario: «Ваш менеджер» в списке

- **WHEN** Анна (программа «Прикладная информатика») открывает `/people`
- **THEN** карточка Беловой содержит плашку «Ваш менеджер»; у Романовой
  (менеджер «Экономика») плашки нет.

#### Scenario: дисциплины студента у преподавателя

- **WHEN** Анна смотрит карточку Ивановой в списке
- **THEN** под должностью видно «Ваши дисциплины: Программирование,
  Алгоритмы и структуры данных».

### Requirement: Карточка человека

Страница `/people/<id>` ДОЛЖНА (MUST) показывать шапку (аватар-инициалы, ФИО,
должность, подразделение, бейджи «Ваш менеджер» / «Ведёт у вас», тип
записи), контакты (почта mailto, кабинет, телефон tel), часы
консультаций, дисциплины преподавателя чипами с пометкой «ваша» у
дисциплин группы студента и кнопки «Написать письмо» (mailto) и
«Записаться на консультацию» (disabled-заглушка с пояснением) — только
у преподавателей. Секция «Ближайшие пары» — только студенту: до 5 будущих
пар его группы с этим преподавателем (от «сейчас», по границам семестра,
без отменённых), каждая ведёт на день расписания; пустое состояние
сформулировано. Внизу — пометка о вымышленности данных.

#### Scenario: карточка преподавателя

- **WHEN** Анна открывает `/people/teacher-ivanova`
- **THEN** видны бейдж «Ведёт у вас», почта `irina.ivanova@example.edu`
  (mailto), кабинет 405, телефон (tel), часы консультаций, дисциплины
  с пометкой «ваша», ближайшие пары с ссылками
  `/schedule?view=day&date=…`, кнопка «Написать письмо» и задизейбленная
  кнопка «Записаться на консультацию» с пояснением.

#### Scenario: метка «Ведёт у вас» едина в списке и карточке

- **WHEN** преподаватель ведёт дисциплину группы студента, но пар с ним
  в расписании сейчас нет
- **THEN** он помечен «его» в списке и получает бейдж «Ведёт у вас» на
  карточке — предикат один и тот же (ревью DIG-37 r2).

#### Scenario: карточка сотрудника

- **WHEN** Анна открывает карточку менеджера Беловой
- **THEN** виден бейдж «Ваш менеджер», контакты и часы консультаций;
  секций «Дисциплины», «Ближайшие пары» и кнопки записи нет — секция
  «Ближайшие пары» не рендерится вовсе: ни заголовка, ни пустого
  состояния с текстом «с этим преподавателем» (ревью DIG-37 r5).

#### Scenario: ближайшие пары студента без совпадений

- **WHEN** студент без будущих пар с преподавателем открывает его карточку
- **THEN** секция показывает «Ближайших пар с этим преподавателем в
  расписании вашей группы нет».

### Requirement: Единый 404 карточки

Неизвестный id (включая битый %-энкодинг сегмента) ДОЛЖЕН (MUST) отвечать
единым 404 (not-found UI) без стриминга оболочки с HTTP 200: в сегменте
`/people/[id]` и его родителях нет loading.tsx.

#### Scenario: неизвестный id

- **WHEN** открывают `/people/no-such-person` или путь с сырым `%`
- **THEN** сервер отвечает 404 (not-found UI), а не пустой экран или 500.

### Requirement: Персонализация только из скоупа сессии

Требование «Персонализация только из скоупа сессии» — обязательное (MUST): Пометки «Мои преподаватели», «Мой деканат», «Ваш менеджер», «Ваши
дисциплины» и «Ближайшие пары» ДОЛЖНЫ вычисляться строго из скоупа
сессии (`ctx.groupName` / `ctx.faculty` / программа студента). id из URL
выбирает запись каталога по белому списку; чужого скоупа в API не
существует по построению. Сотруднику деканата персональные секции не
показываются.

#### Scenario: изоляция персональных пометок

- **WHEN** Анна (ПИ-21, ИТ) и Илья (ЭК-11) открывают один и тот же `/people`
- **THEN** у Анны заполнены «Мои преподаватели» и «Мой деканат» (ИТ), у
  Ильи свои; преподаватель группы ПИ-21 не попадает в «Мои преподаватели»
  Ильи; сотрудники видят общий список без персональных секций.

### Requirement: Переходы из существующих экранов

Из карточки пары в расписании, карточки дисциплины (`/grades/<disciplineId>`) и истории заявки (`/requests/<number>`) имя сотрудника ДОЛЖНО (MUST) быть ссылкой
на `/people/<id>`, если человек есть в справочнике; иначе имя остаётся
обычным текстом без ссылки.

#### Scenario: переход из детали пары

- **WHEN** Анна открывает пару, которую ведёт Иванова
- **THEN** ФИО преподавателя — ссылка на `/people/teacher-ivanova`.

#### Scenario: имя вне справочника

- **WHEN** в расписании/заявке встречается имя, которого нет в каталоге
- **THEN** оно отрисовано обычным текстом, ссылки нет.

### Requirement: Навигация

Раздел «Справочник» ДОЛЖЕН (MUST) быть в боковом меню кабинета (desktop) и в
мобильном «Ещё» с иконкой Contact; href — `/people`.

#### Scenario: пункт меню

- **WHEN** пользователь открывает кабинет
- **THEN** в боковом меню и в «Ещё» есть пункт «Справочник», ведущий на
  `/people`.

### Requirement: Поиск по ФИО с словоформами

На /people — одно поле поиска «ФИО, email или телефон» (плейсхолдер из словаря). ФИО сопоставляется по подстроке и по словоформам: каждое слово запроса должно (MUST) быть началом хоть одного слова нормализованного ФИО (регистр и
«ё» нормализуются).

#### Scenario: словоформа находит человека
- WHEN студент вводит «петр»
- THEN в результатах есть «Петров Пётр Петрович»

#### Scenario: несколько слов запроса
- WHEN студент вводит «иванова ирина»
- THEN в результатах есть «Иванова Ирина Игоревна»; человек без совпадающих
  слов — нет

### Requirement: Поиск по email и телефону

Требование «Поиск по email и телефону» — обязательное (MUST): Email сопоставляется подстрокой без учёта регистра; телефон — подстрокой после
нормализации пробелов и дефисов у обеих строк.

#### Scenario: частичный телефон
- WHEN студент вводит «010-11-22»
- THEN найден человек с телефоном «+7 495 010-11-22»

#### Scenario: пустое состояние поиска
- WHEN по запросу нет совпадений
- THEN показывается «Ничего не найдено» (словарь); до ввода запроса — текущий
  каталог

### Requirement: Одногруппники в поиске

Требование «Одногруппники в поиске» — обязательное (MUST): Студент видит в результатах поиска студентов СВОЕЙ группы (ФИО, email);
сотруднику деканата одногруппники не показываются.

#### Scenario: студент находит одногруппника

- **WHEN** студент группы ЭК-11 ищет по фамилии одногруппника
- **THEN** в результатах есть студент его группы (ФИО, email)

#### Scenario: сотруднику одногруппники не показываются

- **WHEN** сотрудник открывает поиск людей
- **THEN** блок «Одногруппники» не рендерится; выдача поиска — общий справочник

##### Избранное человека

### Requirement: Хранение

Требование «Хранение» — обязательное (MUST): Модель `FavoritePerson` (id, studentId → Student, personId, createdAt; UNIQUE
(studentId, personId)) с миграцией; рантайм-прототип использует memory-адаптер
порта `DataDb` (list/add/remove — owner-scoped по studentId).

#### Scenario: избранное изолировано по владельцу

- **WHEN** студент A добавляет человека в избранное, студент B запрашивает свой список
- **THEN** список B не содержит добавку A (owner-scope по studentId); повторный toggle того же человека удаляет запись (UNIQUE(studentId, personId))

### Requirement: Переключение

Требование «Переключение» — обязательное (MUST): Server action `toggleFavoritePerson(personId)` переключает избранное
владельца сессии. personId валидируется белым списком: id каталога людей или
«groupmate:<Student.id>» студента СВОЕЙ группы (не сам владелец). Сотруднику —
отказ (AuditLog ROLE_MISMATCH).

#### Scenario: toggle добавляет и удаляет
- WHEN студент дважды вызывает toggle для «teacher-petrov» (on/on=false)
- THEN после первого вызова человек в избранном владельца, после второго — нет

#### Scenario: owner-scope
- WHEN студент A добавил человека, студент B запрашивает своё избранное
- THEN список B не содержит избранного A; toggle от имени A не меняет список B
- WHEN студент B пытается добавить «groupmate:<id студента другой группы>»
- THEN отказ без записи

### Requirement: Вкладка «★ Избранное» с категориями

Требование «Вкладка «★ Избранное» с категориями» — обязательное (MUST): На /people есть вкладка «★ Избранное»: список по категориям «Преподаватели» /
«Сотрудники деканата» / «Одногруппники» (словарные ключи), пустые категории
скрываются; пустое избранное — честное empty-state; удаление — кнопкой на
месте. На карточке человека — кнопка-переключатель «★ Добавить в Избранное» /
«★ В Избранном» (Star, aria-pressed).

#### Scenario: категории формируются верно
- WHEN в избранном преподаватель, сотрудник деканата и одногруппник
- THEN три категории содержат по одному человеку каждая; при отсутствии
  одногруппников категория «Одногруппники» не рендерится
