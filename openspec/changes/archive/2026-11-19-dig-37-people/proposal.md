# Proposal: экран «Справочник» — преподаватели и сотрудники (DIG-37)

## Зачем

В аудированном ЛК раздел «Сотрудники» — просто поиск по всем работникам вуза,
а из пары в расписании до преподавателя не дойти: имя — просто текст. В
кабинете нет единого места, где студент видит, кто ведёт его дисциплины, где
найти деканат и менеджера программы, как записаться на консультацию. Задача
добавляет справочник людей с персональными пометками («Мои преподаватели»,
«Мой деканат», «Ваш менеджер») и карточку человека, вшитую в уже существующие
экраны.

## Что

- **Справочник `/people`** (Figma «15 · Справочник», карта `docs/figma-screens.md`):
  - поиск по ФИО, дисциплине и подразделению (клиентский, по одному агрегату
    с сервера; совпадения подсвечиваются `<mark>`);
  - быстрые фильтры пилюлями: «Мои преподаватели» (преподаватели из расписания
    и дисциплин группы студента), «Мой деканат» (сотрудники деканата факультета
    студента), «Все»; фильтры работают совместно с поиском;
  - карточка в списке: аватар-инициалы, ФИО-ссылка на карточку, должность,
    подразделение, дисциплины студента у этого преподавателя; у менеджера
    программы студента — плашка «Ваш менеджер» прямо в списке;
  - скелетон загрузки (route-группа `(list)` — loading не натягивается на
    карточку `/people/<id>`, чтобы не ломать контракт единого 404);
  - пустые состояния: пустой справочник и «никого не нашлось».
- **Карточка человека `/people/<id>`**:
  - шапка: аватар-инициалы, ФИО, должность, подразделение, бейджи
    («Ваш менеджер», «Ведёт у вас»), тип записи (Преподаватель / Сотрудник
    деканата);
  - контакты: почта (mailto), кабинет, телефон (tel);
  - часы консультаций;
  - дисциплины преподавателя (чипами) с пометкой «ваша» у дисциплин группы
    студента;
  - «Ближайшие пары»: до 5 будущих пар группы студента с этим преподавателем
    (от «сейчас», по границам семестра, без отменённых) со ссылкой на день
    расписания; у сотрудника секции нет;
  - кнопки: «Написать письмо» (mailto) и «Записаться на консультацию»
    (заглушка: disabled-кнопка + пояснение — запись появится в обновлении) —
    только у преподавателей;
  - неизвестный id (в т.ч. битый %-энкодинг) — единый 404 без Suspense-
    стриминга (контракт requests).
- **Переходы из существующих экранов** (критерий приёмки):
  - деталь пары (карточка события расписания) — ФИО преподавателя — ссылка;
  - карточка дисциплины `/grades/<disciplineId>` — вместо заглушки «профиль
    появится» — ссылка «Профиль в справочнике»;
  - деталь заявки `/requests/<number>` — имена сотрудников-исполнителей
    (STAFF-акторы) в истории — ссылки.
  - Имя, которого нет в справочнике, остаётся обычным текстом (без ссылки).
- **Навигация**: «Справочник» в боковом меню (desktop) и в мобильном «Ещё»
  (иконка Contact).

## Данные и скоупинг

- Каталог — вымышленный статичный модуль `src/lib/people-catalog.ts`
  (12 записей: 5 преподавателей + 7 сотрудников деканатов ИТ/ЭК и общих
  служб), чистый: без серверных импортов. Имена преподавателей СШИТЫ с сидом
  DIG-12 (`teacherName`) — переход по ФИО работает только для известных людей
  (белый список). Почта только `@example.edu`, телефоны `+7 495 010-xx-xx`,
  бренд вуза не используется.
- Персональные пометки и секции собирает слой `src/server/data/people.ts`
  (`getPeopleDirectory`, `getPersonCard`) СТРОГО из скоупа сессии:
  `ctx.groupName` / `ctx.faculty` / программа студента. IDOR невозможен
  по построению: id из URL выбирает запись каталога по белому списку,
  персональные данные выводятся только из сессии владельца. Контент каталога
  публичный внутри кабинета (контакты вымышленные, как FAQ).

## Правила и допущения (зафиксированы тестами)

- Сотрудник деканата (роль STAFF) видит справочник без персональных секций
  («Ваши дисциплины», «Ближайшие пары», «Ваш менеджер»).
- Сортировка: записи с персональными связями поверх, далее по алфавиту
  (сортировка стабильна относительно каталога).
- Поиск и фильтры — на клиенте: список приходит одним агрегатом, состояние
  поиска не в URL (мгновенный отклик, поиск по вхождению без учёта регистра).

## Отклонения от текста задачи (обоснованные)

- В задаче Figma «10 · Справочник», в карте экранов (`docs/figma-screens.md`)
  фрейм «15 Справочник» → DIG-37; вёрстка по описанию фрейма и токенам
  DIG-13 (FIGMA_TOKEN не задан).
- «Записаться на консультацию» — задизейбленная заглушка с пояснением
  (в задаче прямо сказано «заглушка»), а не скрытая кнопка.

## Non-goals

- Кабинет сотрудника (DIG-48): персональные секции студента ему не
  показываются; редактирование справочника сотрудниками — отдельная задача.
- Реальная запись на консультацию (поток заявок) — вне прототипа.
- Prisma-адаптер: каталог статичный, слой данных читает расписание/дисциплины
  через существующий порт DIG-12.

## Риски / границы

- Справочник виден любому авторизованному (контакты вымышленные).
- `/people/[id]` не имеет loading.tsx ни в одном родительском сегменте
  (список вынесен в route-group `(list)`): Suspense-оболочка стримила бы
  200 до notFound() — контракт единого 404 (как в requests/[number]).
- Rate-limit входа (30 попыток / 15 мин на IP) остаётся как есть: e2e
  справочника логинится per-test, как services.spec — на длинных сериях
  локальных перезапусков лимит требует перезапуска сервера.
