# Proposal: центр уведомлений и панель колокольчика (DIG-35)

## Зачем

В аудированном ЛК центр уведомлений бесполезен: список одинаковых строк
«Сменился статус по обращению сервиса» — без номера, названия и нового
статуса; все помечены «Важно», поэтому метка ничего не значит; последнее
уведомление — 10 сентября, хотя статусы менялись позже; фильтры «Все /
Важные / Непрочитанные» не помогают. Задача закрывает экран Figma
«08 · Уведомления»: колокольчик в шапке с панелью последних 5 уведомлений
и полный экран `/notifications` с конкретными строками (объект + что
изменилось), фильтрами по категориям и группировкой по дням.

## Что

- **Колокольчик в шапке** (`Shell` → `TopBar`): кнопка с бейджем непрочитанных
  (DIG-14), панель последних 5 уведомлений. Клавиатура: открытие с Enter/Space,
  фокус уходит в панель, Tab циклит внутри панели, Esc закрывает и возвращает
  фокус, клик мимо панели закрывает её. Ссылки «Все уведомления» и
  «Настроить уведомления».
- **Экран `/notifications`**: фильтры Все / Непрочитанные / Учёба / Заявки /
  Деканат / Финансы; группировка «Сегодня / Вчера / Ранее» по локальному
  календарю; строка — иконка категории, конкретный заголовок, одна строка
  деталей, время (сегодня/вчера — HH:MM, ранее — DD.MM), точка «не прочитано»,
  метка «Важно» и действие («Скачать», «Открыть расписание»).
- **«Важно»** — только срочное, ставится ИСТОЧНИКОМ уведомления (поле
  `important` строки, не эвристика по тексту): перенос/отмена пары сегодня,
  недопуск, доработка заявки, дедлайн оплаты.
- **Прочтение**: клик по строке (или её действию) отмечает прочитанной
  (server action, скоуп владельца сессии) и ведёт к объекту (soft-nav);
  «Отметить все прочитанными» — разом, только свои строки.
- **Живость без перезагрузки** (критерий приёмки): счётчик в шапке — polling
  `/api/notifications/count` раз в 60 с (DIG-14); лента панели и экрана —
  polling `/api/notifications/recent` раз в 60 с; после server actions экран
  вызывает `router.refresh()` — серверные части (шапка, меню) обновляются
  без полной перезагрузки страницы.
- **Пустые состояния**: иллюстрация колокольчика «Новых уведомлений нет»
  (нет ленты вообще) и «Здесь пока пусто» (под фильтр ничего не подошло);
  сотруднику центр уведомлений недоступен — пустая лента без данных.
- **Сид демо-набора**: уведомления всех категорий с конкретикой
  («Справка для военкомата готова», «Пара «Базы данных» перенесена в ауд.
  Б-204», «Оплата за общежитие — до 25 ноября» и т.д.), все вымышленные.

## Правила и допущения (зафиксированы тестами)

- Скоуп: лента и отметки — только строки владельца сессии (`DataCtx.studentId`),
  URL-параметров нет; чужой id в отметке — `false` + аудит
  (`OWNERSHIP_DENIED`/`NOT_FOUND`), «отметить все» затрагивает только свои
  строки; сотруднику персональной ленты нет (пустой агрегат, без
  аудит-шума на каждый page-view).
- Категории фильтров — отображение типов уведомлений: Учёба = SCHEDULE+GRADE,
  Заявки = REQUEST, Деканат = NEWS+SYSTEM, Финансы = DEADLINE.
- Группировка дней: 0 → «Сегодня», 1 → «Вчера», ≥2 → «Ранее» (локальный
  календарный день; будущие даты — как «сегодня»).
- Панель показывает максимум 5 самых свежих (по `createdAt`, новые сверху).
- `actionLabel` — подпись действия строки; ведёт на `link` строки.

## Non-goals

- Настройки каналов доставки уведомлений — экран «Настройки» (DIG-19),
  из центра только ссылка на него.
- SSE/WebSocket пуш — достаточно polling 60 с (критерий приёмки).
- Генерация уведомлений бизнес-событиями (заявки, оценки) — существующие
  генераторы DIG-19/30; задача не меняет их контракт, кроме поля
  `important`/`actionLabel` в строке.
