# Proposal: экран «Предложение или жалоба руководству» — канал /feedback (DIG-40)

## Зачем

В аудированном ЛК канал был спрятан за пунктом меню «Выразительная кнопка» —
из меню неясно, что за ним стоит (обращение к руководству). Студент не понимает,
куда писать предложения по улучшению, жалобы и благодарности, и не видит, что
из предложенного реально изменилось. По задаче появляется понятный канал
обратной связи `/feedback` с понятным названием и публичной лентой решённых
предложений.

## Что

- **Навигация**: новый раздел «Обратная связь» (`/feedback`) в боковом меню и в
  мобильном «Ещё» — сразу после «Связи с деканатом». Название пункта
  однозначно объясняет назначение (приёмка задачи).
- **Экран `/feedback`** (Figma «18 · Предложения»):
  - «Мои обращения» — список СВОИХ обращений: тип, адресат, номер, статус,
    срок ответа; анонимных в списке нет (у них нет связи с аккаунтом);
  - композер нового обращения: тип (Предложение / Жалоба / Благодарность),
    адресат (Деканат / Учебный офис / Руководство программы / Руководство
    вуза), текст, вложения (до 3 файлов, каждый до 5 МБ — имена, как в
    обращениях DIG-39), переключатель «Анонимно» с объяснением, что увидит
    адресат;
  - лента «Что мы изменили по вашим предложениям» — публичные решённые
    предложения (3 примера в сидах).
- **После отправки** — номер и срок ответа:
  - подписанное обращение → карточка `/feedback/<номер>` (статус «На
    рассмотрении», срок «до ДД месяца», текст и вложения);
  - анонимное → страница подтверждения `/feedback/sent/<номер>`: номер,
    статус, срок и пояснение «обращение не связано с вашим аккаунтом».
- **Анонимность (приёмка)**: анонимное обращение НЕ хранит связь с
  пользователем нигде — в БД `studentId = null`, на клиенте и в ответах API
  никаких пользовательских полей; карточка по номеру анонимного обращения
  отвечает 404 всем (в том числе автору), в списке обращений оно не
  появляется. Подтверждение и статус по номеру — минимальное публичное
  представление без текста и без каких-либо пользовательских данных.
- **Слой данных DIG-12**: owner-scoped чтения/карточка (чужой и
  несуществующий номер — одинаковый 404 + AuditLog), публичный номер
  `FB-ГГГГ-XXXXX` в URL (никогда cuid); публичная лента и страница
  подтверждения — осознанные исключения из owner-scope по образцу
  `findCertificateByCode` (по определению публичные, без пользовательских
  данных в ответе).
- **Срок ответа**: «Рассматриваем обращения в течение 3 рабочих дней» —
  `dueAt = createdAt + 3 рабочих дня` (выходные пропускаются,
  `lib/request-sla`).

## Non-goals

- Интерфейс сотрудника по разбору обращений руководству — вне этой задачи
  (как DIG-48 для обращений в деканат); статусы меняет только слой данных.
- Prisma-модель `Feedback` и миграция — при переезде хранилища на PostgreSQL
  (адаптер к существующему порту); прототип живёт на memory-адаптере DIG-12,
  контракт — порт `DataDb` (как для тикетов DIG-39: сиды БД и сиды
  memory-адаптера живут параллельно).
- Ответ адресата в чате: канал «предложение → результат» одношаговый, без
  переписки (переписка — «Связь с деканатом»).

## Отклонения от текста задачи (обоснованные)

- Макет: в задаче фрейм назван «07 · Деканат — обратная связь», но в карте
  «экран ↔ задача» (`docs/figma-screens.md`) DIG-40 закреплён за
  «18 · Предложения» — вёрстка, код и e2e ссылаются на «18» как на
  канонический номер экрана.
- «Статус в "Обращениях"»: список статусов живёт на самом экране `/feedback`
  («Мои обращения») — общая секция с чатами деканата смешала бы два разных
  мира (тикет с перепиской против одношагового предложения), а отдельный
  пункт меню дублировал бы навигацию.
