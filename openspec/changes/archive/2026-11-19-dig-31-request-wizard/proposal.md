# Proposal: мастер заказа справки или заявления (DIG-31)

## Зачем

DIG-30 дал серверный фундамент (канон «ЗД-…», машина состояний, SLA, PDF
мгновенных типов), DIG-32 — экран списка. Но заказ документа по-прежнему
«упирается в каталог»: ссылки `/requests?order=…` из каталога сервисов (DIG-29)
и FAQ ведут на список заявок, который параметр игнорирует. Аналог в
аудированном ЛК уводит студента во внешний «Центр сервиса» с обезличенным
результатом («Заявка №…») — этого мы и избегаем.

## Что делаем

Мастер заказа **внутри кабинета** (фрейм Figma «06 · Заявки — мастер заказа»):
модальное окно на десктопе (1440), полноэкранный лист на мобильном (360).
Вход: любые ссылки `/requests?order=<id-сервиса>` (каталог, FAQ, CTA
«Заказать справку» на списке заявок) и кнопка списка.

- **Шаг 1 «Что нужно»**: выбранный тип (можно сменить), срок и формат,
  что это за документ — одной строкой.
- **Шаг 2 «Параметры»**: поля зависят от типа (JSON-схема `formSchema`:
  «Назначение» для справки об обучении, «Период/Причина/Дата начала» для
  академического отпуска…), плюс общие поля: куда предоставляется,
  язык (RU/EN), количество экземпляров (1–5), способ получения
  (PDF в кабинете / забрать в деканате / почтой), комментарий,
  вложения (до 5 файлов, до 10 МБ каждый). Данные студента подставлены
  из профиля и не вводятся заново.
- **Шаг 3 «Проверка»**: сводка с «Изменить» у каждого блока,
  согласие «Данные верны», кнопка «Отправить».
- **Успех**: иллюстрация «Справка готова», для мгновенных типов — сразу
  кнопка «Скачать PDF», номер заявки «ЗД-…», ожидаемая дата готовности
  (SLA, рабочие дни), «Следить за статусом» → карточка заявки.

## Решения

- **Валидация на клиенте и на сервере — один словарь правил.**
  Расширяется чистый модуль `lib/request-form-schema.ts` (поля формы,
  по-полевой разбор ошибок) и добавляется `lib/request-wizard-schema.ts`
  (общие поля мастера: язык, экземпляры, способ, комментарий, вложения).
  Server action `createRequestAction` принимает параметры формы и мету
  мастера отдельными полями FormData; сервис `createCanonicalRequest`
  валидирует мету повторно (защита в глубину) и сохраняет её в
  `params` заявки под ключом `wizard` (JSON-строка — тип строки
  `CanonicalRequestRow.params` не меняется).
- **Вложения — метаданные, а не файлы.** В прототипе файлы не передаются
  на сервер: клиент валидирует количество (≤5) и размер (≤10 МБ),
  на сервер уходит JSON-метаданные (имя, размер), валидируемая тем же
  zod-модулем. Хранилище файлов — вне скоупа концепта.
- **Карта «сервис → тип заявки».** `lib/request-order-map.ts` связывает
  id каталога DIG-29 с кодами словаря `RequestType`: cert-enrollment →
  CERT_ENROLLMENT, cert-defer → CERT_ENROLLMENT с предвыбранным
  назначением «для военкомата», cert-grades → GRADES_EXTRACT,
  stmt-academic-leave → ACADEMIC_LEAVE. Неизвестный id (и `order=new`) —
  мастер открывается на шаге 1 без предвыбора, никогда не ошибкой.
- **Черновик не теряется при случайном закрытии:** попытка закрыть мастер
  с заполненными данными (Esc, крестик, подложка) открывает подтверждение
  «Выйти без сохранения?» («Продолжить заполнение» / «Выйти без
  сохранения»).
- **e2e** — на втором демо-студенте (`ilya.petrov`), чтобы не менять
  зафиксированные счётчики пилюль Анны в `e2e/requests.spec.ts`
  (полностью читательный контракт DIG-32).

## Non-goals

- Хранилище и передача вложенных файлов (только метаданные, см. выше).
- Экран «Карточка заявки» с новыми блоками параметров — DIG-33.
- Новые типы заявок в словаре (каталог DIG-29 шире словаря: unmapped-ссылки
  честно открывают мастер без предвыбора).
- Оплата пошлины, статусы «оплачено», интеграции с внешними системами.
