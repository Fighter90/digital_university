# Proposal: экран «Задачи» (DIG-34)

## Зачем

В аудированном ЛК раздел «Задачи» — таблица с одной строкой, дублирующей
заявку из «Заявок»: непонятно, чем задача отличается от заявки. Нужен
единый список **действий**, которые ждут от студента из всех разделов
кабинета. Разделение ролей (критерий приёмки):

- **задача — это действие** («что сделать»): «Доработать заявку»,
  «Сдать: Тест 2», «Записаться на пересдачу», «Ответить на обращение»,
  «Оплатить по договору»;
- **заявка (и любой другой объект) — это объект**: заявку в статусе
  «Нужна доработка» порождает машина состояний DIG-30, но строка задачи —
  не копия заявки, а действие над ней со ссылкой ровно туда, где действие
  выполняется (карточка заявки с формой «Исправить и подать повторно»).

Макет: блок на Figma «03 · Главная» и отдельный экран `/tasks`.
Без `FIGMA_TOKEN` — по описанию задачи и токенам DIG-13 (Inter, Shell,
плашка «Концепт для конкурса» из корневого layout).

## Что

- **Источники задач** (все — слой данных, скоуп по ctx, без URL-параметров):
  1. канонические заявки в статусе «Нужна доработка» (NEEDS_FIX,
     DIG-30) → действие «Доработать заявку» → `/requests/<ЗД-номер>` —
     ровно карточка с формой доработки (legacy «SR-…» карточка формы
     доработки не имеет, поэтому источником служит только канон);
  2. дедлайны заданий по дисциплинам (система курсов; в концепте — сиды
     `StudyDeadlineRow`) → «Сдать: <задание>» → карточка дисциплины
     `/grades/<код>`;
  3. недопуск к экзамену (те же правила допуска, что экран «Сессия»
     DIG-28) → «Сдать: <не сданные элементы>» → `/grades/<код>`;
  4. запись на пересдачу (будущая RETAKE-сессия группы без заявки на
     запись) → «Записаться на пересдачу» → `/grades/session`;
  5. ответ на обращение деканата (обращение с последним сообщением
     сотрудника и не закрытое) → «Ответить на обращение» → `/deanery`;
  6. ручные задачи из сидов (`StudentTaskRow`: подписать документ,
     оплатить по договору) → выполняются кнопкой «Отметить выполненной»
     прямо на экране.
- **Группы сроков**: «Просрочено» (срок в прошлом), «Сегодня», «На этой
  неделе» (1–7 дней), «Позже». Задача без назначенного срока (заявка на
  доработке, ответ на обращение) попадает в «Сегодня» — действие ждёт
  сейчас.
- **Строка задачи**: иконка источника, что сделать (глагол), откуда,
  срок, кнопка действия; для ручных — «Отметить выполненной» (server
  action, владелец проверяется в слое данных, чужой id — единообразный
  отказ + AuditLog).
- **Счётчик в меню**: раздел «Задачи» в боковом меню с числом открытых
  задач (как у уведомлений); раздел также доступен через «Ещё» на
  мобильном.
- **Блок «Что от меня ждут» на главной**: виджет реестра DIG-44 —
  счётчик открытых задач и три самые срочные задачи + ссылка «Все
  задачи» на `/tasks`.
- **Пустое состояние**: «Все дела сделаны 🎉».

## Правила и допущения (зафиксированы тестами)

- Агрегат один — `getTasks(db, ctx)`: все источники читаются параллельно
  (Promise.all); сотрудник получает пустой агрегат и запись AuditLog
  (ROLE_MISMATCH) — тот же контракт, что у «Сессии» (DIG-28).
- Недопуск считается только по будущим контрольным. Для одной дисциплины
  задачи «Сдать: …» с одинаковой причиной (одинаковый набор несданных
  элементов) схлопываются в одну строку с ближайшим сроком: зачёт и
  экзамен по одной дисциплине закрываются одной сдачей.
- Запись на пересдачу не предлагается, если заявка на запись уже
  существует (тот же контракт идемпотентности, что DIG-28) или пересдача
  уже состоялась.
- Ручная задача отмечается только владельцем; отметка идемпотентна;
  чужой или несуществующий id — единообразный отказ, причина — только в
  AuditLog (без оракула существования).
- Данные вымышленные; экраны — Shell, Inter, 1440 и 360 px.

## Non-goals

- Полная интеграция с системой курсов (дедлайны — сиды концепта).
- Отдельные экраны подписания и оплаты: ручные задачи закрываются
  отметкой «выполнено» на самом экране задач.
- Пуш-уведомления о задачах и дедлайнах (экран уведомлений — DIG-35).

## Критерии приёмки (из задачи)

- [ ] Каждая задача ведёт ровно туда, где её выполнить.
- [ ] Нет дублей с заявками: задача — это действие, заявка — объект.
- [ ] Пустое состояние «Все дела сделаны 🎉».
