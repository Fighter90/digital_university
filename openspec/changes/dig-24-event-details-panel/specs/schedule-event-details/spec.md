# Delta: schedule-event-details (DIG-24) — панель «Детали пары»

## ADDED Requirements

### Requirement: Панель деталей пары, управляемая URL

Страница `/schedule` ДОЛЖНА открывать боковую панель деталей пары
(десктоп — справа, <768 px — нижний лист) по URL `?event=<id>`; клик по паре
в любом виде расписания (день, неделя, мобильный список) ведёт на этот URL
с сохранением контекста вида. «Назад» браузера закрывает панель. Состав
панели: тип и цветная полоса, название дисциплины, дата и время; аудитория
и корпус с действием «Как пройти» (схема — заглушка); преподаватель
(ссылка на справочник, email, «Написать»); онлайн-ссылка (если есть);
домашнее задание и материалы (если заданы); «Моя заметка» студента;
действия «Добавить в календарь» (.ics одной пары) и «Спросить AI об этой
паре».

#### Scenario: открытие по клику и по URL

- **WHEN** студент кликает по паре в виде «Неделя» (или карточке дня)
- **THEN** URL получает `event=<id>` без потери `?view`/`?date`, панель
  открыта; повторное открытие по прямой ссылке `?event=<id>` показывает
  ту же панель.

#### Scenario: Esc и фокус

- **WHEN** панель открыта и студент нажимает Esc
- **THEN** панель закрывается, параметр `event` уходит из URL, фокус
  возвращается на блок пары, из которого панель открыли.

#### Scenario: кнопка «Назад»

- **WHEN** студент открыл панель кликом и нажимает «Назад» браузера
- **THEN** панель закрывается (URL возвращается к виду без `event=`).

### Requirement: Изоляция доступа (IDOR)

Доступ к деталям ДОЛЖЕН идти через `getEventDetails(db, ctx, id)` (DIG-21):
чужая пара (другая группа), несуществующий id и сотрудник дают ОДИНАКОВЫЙ
404 (app-wide not-found), причина различима только в AuditLog. Роут
`GET /api/schedule/[id]/ics` отвечает единым JSON 404 по тому же контракту.

#### Scenario: чужая пара по прямой ссылке

- **WHEN** студент группы A открывает `/schedule?event=<пара группы B>`
- **THEN** ответ — 404 (страница not-found), данных пары в ответе нет.

#### Scenario: ICS чужой пары

- **WHEN** студент запрашивает `/api/schedule/<чужой id>/ics`
- **THEN** ответ 404 JSON `{ error: "not_found" }`, идентичный ответу для
  несуществующего id.

### Requirement: Блоки переноса и отмены

Если пара перенесена (`ROOM_CHANGED`/`TIME_CHANGED`), панель ДОЛЖНА
показывать жёлтый блок «Было: <аудитория/время> → Стало: <аудитория/время>»,
причину (`changeNote`) и автора изменения (`changeAuthor`, по умолчанию —
«деканат»). Если отменена (`CANCELLED`) — красный блок с причиной (`note`)
и «Что делать: <восполнение из changeNote>».

#### Scenario: перенос аудитории

- **WHEN** пара `ROOM_CHANGED`: ауд. 214 → 305, причина и автор заданы
- **THEN** в панели «Было: ауд. 214, <время>» → «Стало: ауд. 305, <время>»,
  причина и «Изменил(а): <автор>».

#### Scenario: отмена с восполнением

- **WHEN** пара `CANCELLED` с `note`-причиной и `changeNote`-восполнением
- **THEN** красный блок: «Причина: …» и «Что делать: …».

### Requirement: Заметка студента к паре

Панель ДОЛЖНА позволять создать/изменить и удалить заметку студента к паре
через server actions (контекст из живой сессии, `saveEventNote` /
`deleteEventNote`, лимит 500 символов, пустая не сохраняется). Заметка
видна только владельцу.

#### Scenario: сохранение и удаление

- **WHEN** студент вводит текст и сохраняет
- **THEN** текст сохраняется за студентом и виден при повторном открытии;
  «Удалить» снимает заметку. Чужая пара по прямой ссылке — 404 (панель не
  открывается вовсе).

### Requirement: Экспорт одной пары в календарь

`GET /api/schedule/[id]/ics` ДОЛЖЕН возвращать `text/calendar` с VEVENT
одной пары (UID `event-<id>@digital-deanery`), скоуп — ctx владельца;
контент-Disposition — вложение; Cache-Control — private, no-store.

#### Scenario: своя пара скачивается

- **WHEN** студент скачивает ICS своей пары
- **THEN** 200, тело — VCALENDAR с VEVENT (SUMMARY = «<тип>: <дисциплина>»,
  LOCATION = аудитория/онлайн, DESCRIPTION = преподаватель и статус).
