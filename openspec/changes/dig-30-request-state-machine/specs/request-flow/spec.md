# Delta: request-flow (канонические заявки — DIG-30)

## ADDED

### Requirement: машина состояний заявки

Статус заявки меняется ТОЛЬКО через машину состояний; недопустимый
переход отклоняется ошибкой, а не выполняется молча.

#### Scenario: основная цепочка

- **WHEN** сотрудник проводит `SUBMITTED → ACCEPTED → IN_PROGRESS →
  READY → ISSUED`
- **THEN** каждый переход разрешён машиной

#### Scenario: недопустимый переход

- **WHEN** из `SUBMITTED` запрошен переход сразу в `READY` или из
  терминального (`ISSUED`/`REJECTED`/`CANCELLED`) — любой переход
- **THEN** результат `{allowed: false, code: 'INVALID_TRANSITION'}`

#### Scenario: причины обязательны

- **WHEN** переход в `NEEDS_FIX` или `REJECTED` без непустой причины
  (после trim короче 4 символов)
- **THEN** результат `{allowed: false, code: 'REASON_REQUIRED'}`

#### Scenario: права ролей

- **WHEN** студент запрашивает переход в `ACCEPTED`/`IN_PROGRESS`/
  `READY`/`ISSUED`/`NEEDS_FIX`/`REJECTED`, или сотрудник — в
  `CANCELLED` либо возврат из `NEEDS_FIX` в `SUBMITTED`
- **THEN** результат `{allowed: false, code: 'FORBIDDEN_ACTOR'}`

#### Scenario: отмена студентом до начала работы

- **WHEN** студент-владелец отменяет заявку в статусе `SUBMITTED`,
  `ACCEPTED` или `NEEDS_FIX`
- **THEN** переход `CANCELLED` разрешён; из `IN_PROGRESS` и позже — запрещён

### Requirement: подача заявки

#### Scenario: номер и название

- **WHEN** студент подаёт заявку валидной формы
- **THEN** создан `Request` с номером `ЗД-<текущий год>-<6 цифр>`
  (уникальным) и названием «<тип> · <ключевой параметр>» (без
  ключевого поля — просто тип); записан `RequestEvent` «Подана»
  и создано уведомление с датой готовности по SLA

#### Scenario: мгновенный тип

- **WHEN** подана заявка мгновенного типа (`isInstant`: справка об
  обучении, выписка оценок)
- **THEN** статус сразу `READY`, событие «Документ сформирован
  автоматически», уведомление «готова к скачиванию»

#### Scenario: повторный заказ за 24 часа

- **WHEN** студент повторно заказывает тот же ДОКУМЕНТ — тот же тип
  И то же значение ключевого поля формы (`keyField`), а его заявка
  с такими типом и параметром в статусе `READY`/`ISSUED` создана
  менее 24 часов назад
- **THEN** новая заявка НЕ создаётся; ответ `{kind: 'duplicate',
  existing}` с номером готовой — UI предлагает скачать документ

#### Scenario: тот же тип с другим ключевым параметром

- **WHEN** готовая справка «для банка» существует, студент заказывает
  справку того же типа с назначением «для военкомата»
- **THEN** создаётся НОВАЯ заявка (`created`) — это другой документ;
  дубликат ключуется парой «тип + ключевой параметр» (решение по
  замечанию ревью DIG-30, раунд 3)

#### Scenario: форма валидируется zod'ом

- **WHEN** параметры не соответствуют JSON-схеме типа (required,
  enum, date, maxLength), в том числе дата существует только «на
  бумаге» (`2026-02-30`, `2026-13-45` — формат верный, календаря нет)
- **THEN** заявка не создаётся, ответ `INVALID_FORM` с сообщением
  первого нарушения

### Requirement: переходы через сервис (права и аудит)

#### Scenario: студент не может перевести в READY

- **WHEN** студент-владелец вызывает `transitionCanonicalRequest` в
  `READY`
- **THEN** ответ `FORBIDDEN` (машина: пара `→ READY` существует только
  для сотрудника), строка не меняется

#### Scenario: чужая заявка неотличима от несуществующей

- **WHEN** студент обращается к переходу/чтению чужой или
  несуществующей заявки
- **THEN** ответ `NOT_FOUND` / null в обоих случаях, попытка чужой
  записана в аудит (`OWNERSHIP_DENIED`)

#### Scenario: сотрудник ограничен факультетом

- **WHEN** сотрудник выполняет переход по заявке студента другого
  факультета
- **THEN** ответ `NOT_FOUND`, отказ `OUTSIDE_FACULTY` в аудите

#### Scenario: каждый переход пишет событие и уведомление

- **WHEN** разрешённый переход выполнен
- **THEN** добавлен `RequestEvent` (актор, роль, from→to, комментарий)
  и создано уведомление вида «Заявка ЗД-2026-000123 «Справка об
  обучении · для военкомата»: Принята → В работе. Готовность до
  <дата по SLA>» (для `NEEDS_FIX`/`REJECTED` — с причиной)

#### Scenario: дата готовности считается от момента перехода

- **WHEN** переход выполняется позже подачи (поздний `ACCEPTED`,
  `IN_PROGRESS`, возврат `NEEDS_FIX` → `SUBMITTED` после доработки)
- **THEN** «Готовность до …» в уведомлении считается от момента
  перехода (`now`), а не от `createdAt` — обещание никогда не
  указывает на дату в прошлом (решение по замечанию ревью
  DIG-30, раунд 3)

### Requirement: скачивание документа мгновенной заявки

#### Scenario: владелец скачивает готовую справку

- **WHEN** студент-владелец запрашивает документ заявки в `READY`
  мгновенного типа
- **THEN** `200 application/pdf` («Справка об обучении» — собственный
  PDF, «Выписка оценок» — выписка из зачётки)

#### Scenario: чужой / неготовый / бумажный — единый 404

- **WHEN** документ запрашивает не владелец, либо заявка не в
  `READY`/`ISSUED`, либо тип бумажный (документа нет), либо номер не
  канонический — в том числе сегмент с «сырым» процентом
  (`/api/requests/%25/document`): декодирование номера обязано быть
  безопасным и не ронять роут с 500
- **THEN** одинаковый ответ 404 без раскрытия причины
