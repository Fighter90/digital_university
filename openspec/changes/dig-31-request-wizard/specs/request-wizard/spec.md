# Delta-спека: мастер заказа справки или заявления (DIG-31)

## ADDED — Requirement: заказ документа мастером в 3 шага

Кабинет студента МОЖЕТ принимать заказ справки или заявления через мастер
из трёх шагов («Что нужно» → «Параметры» → «Проверка») внутри кабинета:
модальное окно на десктопе, полноэкранный лист на мобильном (360 px).

### Scenario: вход в мастер из каталога с предвыбором типа

- **WHEN** студент открывает `/requests?order=cert-defer` (ссылка каталога
  сервисов или FAQ)
- **THEN** мастер открыт на шаге 1 «Шаг 1 из 3», тип «Справка об обучении»
  уже выбран (можно сменить в списке типов), рядом срок и формат документа
  и одна строка «что это за документ»

### Scenario: шаг «Параметры» зависит от типа

- **WHEN** студент переходит на шаг 2, выбрав тип
- **THEN** показаны поля JSON-схемы типа (для CERT_ENROLLMENT —
  «Назначение», для ACADEMIC_LEAVE — «Период», «Причина», «Дата начала»),
  общие поля мастера (куда предоставляется, язык RU/EN, количество
  экземпляров 1–5, способ получения: PDF в кабинете / забрать в деканате /
  почтой, комментарий, вложения до 5 файлов по ≤10 МБ) и блок «Данные
  из профиля» (ФИО, группа, курс, факультет), доступный только для чтения

### Scenario: проверка и согласие

- **WHEN** студент на шаге 3 «Шаг 3 из 3»
- **THEN** показана сводка по блокам «Документ», «Параметры», «Данные
  студента», у каждого блока кнопка «Изменить», отправка недоступна без
  отметки «Данные верны»

## ADDED — Requirement: валидация мастера на клиенте и на сервере

Мастер МОЖЕТ отклонять некорректный ввод на клиенте по-полевыми понятными
ошибками и на сервере (server action + сервис заявок) — одним и тем же
набором правил; сервер НЕ сохраняет заявку при нарушении любого правила.

### Scenario: обязательное поле формы не заполнено

- **WHEN** студент на шаге 2 оставляет «Назначение» пустым и нажимает «Далее»
- **THEN** под полем появляется «Заполните поле «Назначение»», шаг не меняется;
  попытка отправки такого же набора на сервер отвечает ошибкой без создания
  заявки

### Scenario: вложения сверх лимита

- **WHEN** студент выбирает 6 файлов или файл больше 10 МБ
- **THEN** мастер показывает ошибку лимита и не отправляет метаданные на сервер;
  сервер повторно отклоняет мету с теми же лимитами

## ADDED — Requirement: черновик не теряется при случайном закрытии

Мастер МОЖЕТ запрашивать подтверждение при закрытии с заполненными данными.

### Scenario: Esc с заполненным черновиком

- **WHEN** студент нажимает Esc (крестик или подложку) при заполненном
  черновике
- **THEN** появляется подтверждение «Выйти без сохранения?» с «Продолжить
  заполнение» и «Выйти без сохранения»; «Продолжить заполнение» возвращает
  в мастер с сохранёнными значениями

## ADDED — Requirement: результат заказа

Мастер МОЖЕТ показывать результат с конкретикой заявки (не обезличенно).

### Scenario: мгновенная справка

- **WHEN** студент отправляет заказ мгновенного типа (CERT_ENROLLMENT,
  GRADES_EXTRACT)
- **THEN** экран успеха показывает «Справка готова», иллюстрацию, номер
  заявки «ЗД-…», кнопку «Скачать PDF» (готовый документ) и «Следить за
  статусом»

### Scenario: обычная заявка

- **WHEN** студент отправляет заказ немгновенного типа
- **THEN** экран успеха показывает «Заявка отправлена», номер «ЗД-…»,
  ожидаемую дату готовности по SLA (рабочие дни) и «Следить за статусом»

### Scenario: повторный заказ за 24 часа

- **WHEN** сервер отвечает «дубликат» (та же справка уже готова)
- **THEN** мастер показывает «Справка уже готова», номер существующей заявки
  и кнопку «Скачать PDF», новая заявка не создаётся

## ADDED — Requirement: точка входа и роли

Мастер МОЖЕТ открываться из каталога, FAQ и списка заявок и быть доступен
только студенту.

### Scenario: сотрудник мастера не видит

- **WHEN** сотрудник открывает `/requests?order=…`
- **THEN** мастер не рендерится, список остаётся в состоянии сотрудника

### Scenario: неизвестный параметр заказа

- **WHEN** студент открывает `/requests?order=неизвестный-сервис`
- **THEN** мастер открывается на шаге 1 без предвыбора типа; ошибки нет
