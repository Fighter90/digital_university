# DIG-33 — Экран «Карточка заявки»: история, доработка, документ

## Зачем

Аудит ЛК-аналога показал боль: заявка месяцами висела в «Доработке» без
причины, срока и кнопки действия; время создания в списке и в карточке
расходилось (разные часовые пояса рендера). Карточка заявки (Figma
«06 · Заявки — карточка», DIG-32 заложила каркас) должна сама отвечать на
все вопросы студента: что происходит, кто ведёт, когда ждать, что исправить,
где документ и как спросить деканат.

## Что

- **Шапка карточки «ЗД-…»**: название, номер с кнопкой «Копировать»,
  статус-пилюля, степпер конвейера (DIG-32), ожидаемая дата готовности
  (SLA типа от момента последнего «вперёд»-перехода, `request-sla.ts`),
  «Ведёт: <имя сотрудника>» — по последнему STAFF-событию истории.
- **NEEDS_FIX**: красный блок с причиной сотрудника + форма исправления
  прямо в карточке (текстовое поле «что исправлено») и кнопка
  «Отправить повторно» → `NEEDS_FIX → SUBMITTED` машиной состояний DIG-30,
  событие с комментарием студента пишется в историю.
- **READY + PDF**: блок документа — превью PDF (`?inline=1` у роута
  документа), «Скачать PDF», «Проверить подлинность» (страница проверки
  `/verify` — вход по коду из PDF), «Отправить на email» (концепт:
  SMTP не подключается, фиксируется кабинетное уведомление об отправке
  на email профиля).
- **Параметры заявки**: поля формы типа (labels из JSON-схемы) и мета
  мастера заказа (язык, куда предоставляется, экземпляры, способ,
  комментарий) и вложения (имена файлов + размеры из меты мастера).
- **История**: вертикальный таймлайн событий (точка+линия), автор,
  переход/статус, комментарий, время.
- **Время — одна зона**: все метки времени заявок (список, карточка,
  события) форматирует один форматтер `formatRequestDate` с явной зоной
  Europe/Moscow и суффиксом «МСК» — часовому поясу пользователя
  прототипа (конвенция проекта: schedule-time, PDF-документы, MCP).
  Host-пояс сервера больше не протекает в UI.
- **Действия**: «Отменить» (до «В работе», существующая машина состояний),
  «Задать вопрос по заявке» → создаёт обращение в деканат с темой
  «Вопрос по заявке ЗД-…» и текстом вопроса (новая data-функция).
- **Демо-данные**: второму студенту (Илья) — две канонические заявки
  (мгновенная READY + «нужна доработка»), чтобы e2e-мутации экрана
  не задевали зафиксированный мир Анны (пилюли DIG-32, бейдж DIG-54/35).
- Публичная страница `/verify` (без кода): объяснение, поле ввода кода
  → `/verify/<код>`; путь добавлен в точные публичные роуты гварда.

## Non-goals

- Реальная отправка email (SMTP) — концепт фиксирует отправку уведомлением.
- Регистрация канонических документов в реестре справок DIG-47
  (CertificateIssue.requestId — FK на legacy Request; отдельная задача).
- Кабинет сотрудника по заявкам (DIG-48), раздел обращений (DIG-39).

## Risks

- Суффикс «МСК» меняет метки во всех экранах заявок — e2e DIG-32 метки
  времени не пинит (проверено grep'ом); юнит-тесты карточек используют
  мок-строки.
- Мутационные e2e живут только на заявках Ильи; Анна остаётся
  read-only (контракт DIG-32).
