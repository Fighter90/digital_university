# Delta — DIG-126: канонические заявки (ЗД-…) в кабинете сотрудника
# (capabilities: staff-cabinet, canonical-requests)

## MODIFIED

### Requirement: Очередь заявок сотрудника — единая для канона и легаси
(capability staff-cabinet)

Очередь /staff/requests показывает заявки студентов факультета сотрудника
ОБЕИХ миров: легаси-сиды (ЗС/SR-…) и канонические заявки мастера (ЗД-…,
DIG-30). Строка канона несёт пилюлю «Заявка мастера», номер ЗД- и
SLA-дедлайн из `etaDays` типа (РАБОЧИЕ дни); легаси-строки и их SLA не
меняются. Скоуп факультета — из ctx сотрудника; канон чужого факультета в
очереди отсутствует.

#### Scenario: Канон-заявка видна в очереди

- WHEN сотрудник факультета «ИТ» открывает /staff/requests, а студент
  факультета «ИТ» подал канон через createCanonicalRequest (статус
  SUBMITTED)
- THEN очередь содержит строку с `data-kind="canonical"`, номером «ЗД-…»,
  пилюлей «Заявка мастера» и SLA-подсветкой от etaDays типа
- AND легаси-строки (ЗС/SR-…) рендерятся как прежде

#### Scenario: Канон чужого факультета невидим

- WHEN канон принадлежит студенту другого факультета
- THEN строки в очереди нет (и по фильтрам её не получить)

#### Scenario: «Взять в работу» канона из очереди

- WHEN сотрудник нажимает «Взять в работу» на канон-строке в SUBMITTED
- THEN выполняется ЛЕГАЛЬНАЯ цепочка машины DIG-30
  SUBMITTED → ACCEPTED → IN_PROGRESS (два события истории, два
  уведомления владельцу)
- AND строка ре-рендерится в группе «В работе»

### Requirement: Карточка заявки сотрудника — единый маршрут для ЗД-… и SR-…
(capability staff-cabinet)

Маршрут /staff/requests/[номер] понимает оба формата. Номер канона
(«ЗД-ГГГГ-NNNNNN») рендерит карточку канона: данные студента (контакты —
по разрешениям), параметры из JSON-схемы типа и мета мастера, история
канона, легальные переходы машины DIG-30 для роли STAFF (причина
обязательна у «Доработки» и «Отказа»; терминальные статусы без формы).
Легаси-номер («SR-…») — прежний поток без изменений. Чужой факультет и
несуществующий номер — единый 404 (без оракула существования), попытка —
в аудите.

#### Scenario: Сотрудник открывает карточку канона своего факультета

- WHEN сотрудник факультета владельца открывает /staff/requests/ЗД-…
- THEN видит заявку (название, статус, тип словаря DIG-30), студента,
  параметры формы и мета мастера, историю канона и форму переходов по
  allowedRequestTransitions(status, 'STAFF')

#### Scenario: Чужой факультет — единый 404

- WHEN сотрудник открывает ЗД-… студента другого факультета (или
  несуществующий номер)
- THEN ответ — 404 (не 200-скелетон), попытка чужого — в аудите как
  OUTSIDE_FACULTY

#### Scenario: Переходы канона легальны

- WHEN сотрудник меняет статус канонической заявки
- THEN переход проверяется машиной DIG-30 (проверка и в слое данных);
  недопустимый переход или отсутствие обязательной причины отклоняется с
  ошибкой, ничего не меняя

## ADDED

### Requirement: Канон-очередь сотрудника — owner-scope чтение факультета
(capability canonical-requests)

`listCanonicalRequestsForStaff` возвращает канонические заявки студентов
факультета из ctx (STAFF); студенту и сотруднику без факультета — [] с
аудитом ROLE_MISMATCH. Порт `listCanonicalRequestsByFaculty` фильтрует
строки через владельцев факультета.

#### Scenario: Сотрудник читает очередь канона

- WHEN ctx — STAFF с факультетом «ИТ»
- THEN результат — только канон-заявки студентов «ИТ», по свежести подачи

#### Scenario: Студент вызывает staff-чтение

- WHEN ctx — STUDENT
- THEN результат [] и запись в аудите (resourceType canonical-request,
  reason ROLE_MISMATCH)

### Requirement: «Взять в работу» канона — легальная цепочка машины DIG-30
(capability canonical-requests)

`takeCanonicalRequestInProgress(number)` для сотрудника факультета
владельца: из SUBMITTED — цепочка SUBMITTED → ACCEPTED → IN_PROGRESS
(каждое звено через `transitionCanonicalRequest`: событие истории +
уведомление), из ACCEPTED — один шаг; иной статус — NOT_ALLOWED; чужой
факультет и несуществующий номер — NOT_FOUND (аудит отказа).

#### Scenario: Сквозной контур DIG-126

- WHEN студент подал канон (createCanonicalRequest), сотрудник увидел его
  в очереди и выполнил «Взять в работу»
- THEN заявка в статусе IN_PROGRESS, история содержит события
  SUBMITTED → ACCEPTED → IN_PROGRESS, студент видит «В работе» в своих
  заявках и получил уведомления
