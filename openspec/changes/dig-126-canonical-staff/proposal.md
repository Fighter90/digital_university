# DIG-126 — P0: канонические заявки (ЗД-…) в кабинете сотрудника

## Зачем

Регресс DIG-110 (FINDINGS-108, дефект **D1**): заявка, поданная студентом
через мастер `/requests` (канон DIG-30, номера «ЗД-2026-000010»), НЕ
появляется в очереди `/staff/requests` и карточка `/staff/requests/ЗД-…`
отвечает 404. Подтверждено на проде. Причина — слои не стыкованы:

- мастер пишет в канон-таблицу (`createCanonicalRequest` →
  `insertCanonicalRequest`);
- кабинет сотрудника читает ТОЛЬКО легаси: `getStaffQueue` →
  `db.listRequestsByFaculty`, карточка — `probeRequestByNumber`,
  переходы — `updateRequestByStaff`;
- `src/app/(cabinet)/staff/**` не знает про canonical.

Разорван основной продуктовый контур «студент подал → сотрудник взял в
работу → студент видит статус» для всего нового потока заявок. P0 для
конкурса: жюри проходит именно мастер-заявку.

## Что делаем (интеграция слоёв)

- **Порт**: `listCanonicalRequestsByFaculty(faculty)` + реализация в
  memory-адаптере (сквозь владельцев факультета, по свежести подачи).
- **Сервис канона** (`canonical-requests.ts`): `listCanonicalRequestsForStaff`
  (owner-scope из ctx, студенту — [] + аудит ROLE_MISMATCH),
  `takeCanonicalRequestInProgress` («Взять в работу» легальной цепочкой
  SUBMITTED → ACCEPTED → IN_PROGRESS — каждое звено пишет машину переходов:
  событие истории + уведомление), `staffTransitionCanonicalRequest`
  (переход по номеру ЗД с проверкой факультета).
- **Сервис сотрудника** (`staff-workflow.ts`): `getStaffQueueUnified` —
  ЕДИНАЯ очередь двух миров (легаси ЗС/SR не ломается): канон спроецирован
  на строку очереди с `kind: 'canonical'` и SLA-дедлайном из `etaDays`
  типа РАБОЧИМИ днями; `getStaffCanonicalRequestDetail` — карточка канона
  (заявка + студент + история + тип словаря + контакты по разрешениям).
- **Очередь `/staff/requests`**: канон-строки рядом с легаси — пилюля
  «Заявка мастера», номер ЗД- (EN — транслит ZD-), SLA-подсветка от
  дедлайна канона, «Взять в работу» канона отдельным action.
- **Карточка `/staff/requests/ЗД-…`**: ветка `isValidCanonicalRequestNumber`
  — параметры из JSON-схемы типа + мета мастера, история канона
  (RequestHistoryTimeline), форма легальных переходов машины DIG-30
  (`CanonicalRequestStatusForm`: Принять / Взять в работу / Готова к
  выдаче / Нужна правка данных / Отклонить; причина обязательна у
  доработки и отказа). Чужой факультет и несуществующий номер — единый 404.
- **i18n RU/EN парой**: `staff.queue.canonicalPill`,
  `staff.canonicalType.*` (6 кодов словаря); EN — ноль кириллицы
  (транслит номера, ключи типов).
- **Сид**: канон-заявки в очереди сотрудника уже есть из коробки
  (Анна, «ИТ»: SUBMITTED «Дубликат диплома», NEEDS_FIX «Справка об
  обучении») — демо non-empty, фикс подтверждён тестом.

## Non-goals

- Легаси-мир (ЗС/SR-…) не меняется: `getStaffQueue`/`getStaffRequestDetail`/
  `changeStaffRequestStatus` — прежние контракты (сосуществование).
- Сводка `/staff` (метрики «заявок сегодня») остаётся на легаси-очереди —
  отдельная задача, не часть интеграции D1.
- Prisma-адаптер: memory-порт расширяется симметрично, SQL-адаптер —
  при миграции слоя (как DIG-12/DIG-50).

## DoD

- Сквозной тест зелёный: `createCanonicalRequest` → сотрудник видит в
  очереди → «Взять в работу» → студент видит «В работе» (юнит-сквозной +
  e2e staff-cabinet).
- Owner-scope тесты: чужой факультет — 404 карточки / пустая очередь,
  попытка — в аудите (OUTSIDE_FACULTY / ROLE_MISMATCH).
- `node scripts/swarm/gates.mjs` → GATES_SUMMARY: green.
