# Proposal: кабинет сотрудника деканата — очередь заявок, обращения, объявления (DIG-48)

## Зачем

Со стороны студента не видно, кто и как обрабатывает заявку, — отсюда
«висящие» статусы. Чтобы показать, как студент получает быстрый и понятный
ответ, нужна вторая роль: вход под `staff` (демо-логин `dean.kovaleva`),
кабинет сотрудника деканата (Figma «27 · Кабинет сотрудника»). Сотрудник
разбирает очередь заявок, отвечает на обращения и объявляет новости —
студент сразу видит результат в своём кабинете.

## Что

- **Очередь заявок** `/staff/requests`: все заявки студентов СВОЕГО
  факультета, сгруппированы по статусам; фильтры по типу заявки и по сроку
  (все / просроченные / сегодня / неделя); подсветка просроченных по SLA
  (дни на ответ по типу: справка 3, заявление 5, практика и общежитие 7,
  прочее 5); кнопка «Взять в работу» прямо из очереди.
- **Карточка заявки сотрудника** `/staff/requests/[номер]`: данные студента
  (ФИО, группа, курс, зачётка, программа; email/телефон — только если
  студент разрешил показ), параметры и история, смена статуса кнопками —
  только разрешённые переходы (SUBMITTED → в работу/доработка/отказ;
  IN_PROGRESS → выполнена/доработка/отказ; NEEDS_REVISION → в работу/отказ),
  «Нужна доработка» и «Отклонить» требуют причину (≥ 5 символов),
  «Сформировать PDF» для выполненной заявки-справки (механика DIG-47:
  код проверки, QR, тот же код при повторном формировании).
- **Обращения** `/staff/appeals[/id]`: входящие обращения студентов
  факультета, чат с шаблонами ответов (кнопка подставляет текст), ответ
  переводит обращение в ANSWERED, «Решено» — закрывает.
- **Объявления** `/staff/announcements`: создать объявление для факультета
  или группы (группа проверяется на принадлежность факультету), живой
  предпросмотр до публикации, список опубликованных.
- **Сводка** `/staff`: заявок сегодня, среднее время ответа (часы, по
  событиям сотрудников), просрочено по SLA, счётчики по статусам, свежие
  обращения.
- **Уведомление студенту**: любая смена статуса сотрудником и ответ/закрытие
  обращения пишут уведомление в ленту студента синхронно (тот же вызов слоя
  данных, что и запись статуса) — студент видит его при первом же обновлении
  (< 60 с); уведомление ведёт на карточку заявки/в деканат. Матрица каналов
  и тихие часы студента на события деканата не влияют (важное собственное
  событие всегда доходит в кабинет).
- **403 для студента**: middleware возвращает 403 на любой `/staff*` при
  роли STUDENT или отсутствии подписанного role-hint (fail closed);
  страницы дополнительно перепроверяют роль серверно (requireStaff-подход).
- **Навигация**: Shell общий, боковое меню и таб-бар строятся по роли
  (у сотрудника — Сводка / Заявки / Обращения / Объявления).

## Non-goals

- Отзыв справок из интерфейса сотрудника (API DIG-47 уже существует; кнопка
  в UI — отдельная задача).
- Лента новостей студента из объявлений (DIG-36) и экран уведомлений
  студента (DIG-35): события пишутся в данные, UI подключения — там.
- Ответы студента в обращениях и смена статуса студентом (сейчас только
  чтение истории).
- Prisma-адаптер и PostgreSQL: прототип живёт на memory-адаптере, как весь
  кабинет; сигнатуры порта готовы к транзакционному адаптеру.
- Канбан drag-n-drop: очередь — таблица/карточки по статусам с фильтрами.

## Риски

- Много новых экранов: закрыто unit-тестами страниц (SSR-рендер) и e2e
  основного сценария (десктоп 1440 и мобайл 360).
- IDOR по номеру заявки/обращения: скоуп факультета проверяется слоем
  данных по студенту-владельцу, чужое и несуществующее — одинаковый
  ответ + запись в аудит (контракт DIG-12 не меняется).
- Смена статуса «кто угодно кому угодно»: белая карта разрешённых
  переходов в чистой функции, повторная проверка в слое данных (от
  текущего статуса строки), событие истории пишет актёра.
