# Изоляция данных (DIG-12)

## Requirement: Доступ к данным только через контекст сессии

Каждое чтение/изменение данных выполняется функцией `src/server/data/*`,
которая принимает `DataCtx` (собирается из сессии `requireUser()`, никогда —
из URL). Студент скоупится `studentId` и своей группой, сотрудник —
факультетом. Прямой импорт Prisma-клиента вне `src/server/` запрещён
правилом ESLint `no-restricted-imports` и закреплён тестами.

#### Scenario: Чужая заявка по номеру неотличима от несуществующей

- **WHEN** Анна открывает `/requests/<номер заявки Ильи>` (страница или API)
- **THEN** обе поверхности отвечают одинаковым 404 (страница-404 / JSON
  `{ error: 'not_found' }`), факт существования заявки Ильи не раскрывается,
  попытка попадает в AuditLog с причиной OWNERSHIP_DENIED

#### Scenario: Своя заявка открывается

- **WHEN** владелец открывает `/requests/<свой номер>`
- **THEN** он видит статусную модель заявки и историю событий

#### Scenario: Студент не проходит в staff-функции

- **WHEN** студент вызывает staff-функции слоя (или сотрудник — студенческие)
- **THEN** ответ пустой/нулевой (как «нет данных»), попытка записана в аудит
  с ROLE_MISMATCH

## Requirement: Сотрудник видит только студентов своего факультета

Факультет берётся из Staff-профиля сессии, не из ввода.

#### Scenario: Студент чужого факультета не отдаётся

- **WHEN** сотрудник факультета ИТ запрашивает студента факультета ЭК
- **THEN** ответ идентичен «студент не существует» (404-семантика), в аудите
  OUTSIDE_FACULTY

## Requirement: Аудит попыток чужого доступа

`denyAccess()` — единственная точка записи DENIED-событий (actor, resource,
ref, причина). Пишется и при OWNERSHIP_DENIED (объект существует), и при
NOT_FOUND (зондирование), и при OUTSIDE_FACULTY/ROLE_MISMATCH.

#### Scenario: Аудит не ломает ответ

- **WHEN** хранилище аудита недоступно
- **THEN** HTTP-ответ не меняется (по-прежнему единый 404), ошибка аудита
  проглатывается

## Requirement: Публичные номера не последовательные

Заявка адресуется номером `SR-<год>-<5 A-Z0-9>` (случайный суффикс),
id (cuid) в URL сущностей не раскрывается; нормализация номера
(регистр, «#», пробелы) происходит до поиска, но проверку владельца это
не отменяет.

#### Scenario: Номер не раскрывает порядок заявок

- **WHEN** два номера заявок сгенерированы подряд
- **THEN** они различаются случайным суффиксом и не дают информации о
  количестве/порядке заявок в системе

## Requirement: Prisma — только в src/server/

ESLint `no-restricted-imports`: `@prisma/client`, `@prisma/adapter-*`,
сгенерированный клиент — запрещены вне `src/server/`.

#### Scenario: Регрессия ловится линтом

- **WHEN** в компоненте или на странице появляется импорт Prisma
- **THEN** `npm run lint` падает с `no-restricted-imports` (тест
  `tests/eslint-isolation-rule.test.ts` закрепляет поведение на виртуальных
  файлах)

## Delta к схеме БД (интеграция с DIG-9/DIG-10 при смерже)

- `ServiceRequest.number String @unique` — публичный номер (формат выше);
  URL экранов и API использует только его.
- `Staff.faculty String` — факультет сотрудника для скоупа.
- `AuditLog` — модель аудита: `actorUserId?`, `actorLogin?`, `actorRole?`,
  `resourceType`, `resourceRef`, `reason (enum DenialReason)`, `outcome`,
  `createdAt`; индекс по `actorUserId, createdAt`.
- `ScheduleEvent`/`ExamSession` — уже скоупятся по `groupName` (схема DIG-9);
  слой данных отдаёт только группу контекста.
- Адаптер: `createPrismaDataDb(client)` реализует порт `DataDb` 1:1 по
  типам `src/server/data/types.ts`; переключение — одна строка в
  `src/server/data/db.ts`.
