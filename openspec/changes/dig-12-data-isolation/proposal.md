# DIG-12 — Изоляция данных: студент видит только свои данные (защита от IDOR)

## Зачем

Требование ТЗ: «чужой профиль или чужую заявку не открыть, даже подставив
другой адрес». DIG-11 дал точку входа сессии (`requireUser()`), но проверка
владельца оставалась дисциплиной каждого экрана. DIG-12 делает изоляцию
**архитектурной**: единственный способ дотянуться до данных — функции
`src/server/data/*`, у которых фильтр по владельцу вшит в сигнатуры и
написание «забыть фильтр» невозможно.

## Что сделано

- **DataCtx** (`src/server/data/types.ts`) — контекст доступа, собираемый из
  сессии (`requireUser()` → `toDataCtx()`): студент получает `studentId` +
  своя группа, сотрудник — свой факультет. URL-параметры в контекст не
  попадают никогда.
- **Слой `src/server/data/*`** — по модулю на сущность (requests, grades,
  notifications, appeals, schedule, staff). Каждая функция принимает `db`
  (порт `DataDb`) и `ctx`: чтение списков всегда с фильтром владельца,
  доступ по одному объекту (номер заявки / cuid / id) перепроверяет
  владельца через существование-пробу **внутри** слоя.
- **Единый 404 без оракула существования**: чужой и несуществующий объект
  дают одинаковый ответ (страница `src/app/not-found.tsx`, для API —
  `uniformNotFoundResponse()` с телом `{ error: 'not_found' }`). Различие
  есть только в AuditLog.
- **AuditLog**: каждая попытка доступа к чужому/несуществующему объекту
  пишется через `denyAccess()` (actor, resource, ref, причина
  OWNERSHIP_DENIED / OUTSIDE_FACULTY / ROLE_MISMATCH / NOT_FOUND).
- **Сотрудник видит только студентов своего факультета** —
  `listFacultyStudents()` / `getFacultyStudent()` фильтруют по факультету из
  Staff-профиля сессии; студент в staff-функциях получает пустой ответ и
  запись в аудите.
- **Не-последовательные публичные номера заявок** `SR-<год>-<5 A-Z0-9>`
  (`request-number.ts`): URL не раскрывает порядок и количество заявок.
- **ESLint `no-restricted-imports`** (`eslint.config.mjs`): `@prisma/client`,
  `@prisma/adapter-*` и сгенерированный клиент запрещены вне `src/server/`;
  правило закреплено тестами `tests/eslint-isolation-rule.test.ts`.
- **Порт + in-memory адаптер** (`port.ts`, `memory-db.ts`): сигнатуры порта
  требуют область видимости в каждом вызове; адаптер в памяти обслуживает
  тесты и работающий прототип до смержа DIG-10 (конвенция DIG-11).
- **Демо-данные жюри** (`demo-seed.ts`): вымышленные Анна (ИТ), Илья (ЭК),
  сотрудник Мария (ИТ) с заявками/оценками/уведомлениями; сид идемпотентен и
  запускается до первого входа (страница логина). Пароли демо — публичные по
  дизайну (конкурсный прототип, реальные ПДн запрещены).
- **Экраны**: `/requests` (список своих заявок) и `/requests/[номер]`
  (детальная с историей статусов), API `GET /api/requests/[номер]` — первые
  потребители слоя, шаблон для будущих ICS/PDF/AI-фидов.
- **e2e (red-first)**: `e2e/data-isolation.spec.ts` — чёрно-ящичный сценарий:
  Илья логинится, его номер заявки читается из его списка; Анна логинится и
  открывает этот номер — страница и API отвечают одинаковым 404; несуществующий
  номер — тот же ответ; своя заявка открывается. Также аноним не доходит до
  данных (редирект на /login).
- **Фикс dev-инфраструктуры** (потребовался самим критерием e2e-API):
  синглтоны auth-стора и dataDb переведены на `globalThis`-кэш — в dev-mode
  Next.js/Turbopack держит отдельные server-бандлы для страниц и API-роутов,
  и модульный синглтон давал роуту ПУСТОЕ хранилище (сессия «не находилась»).
  Аналогично закреплён `turbopack.root` в `next.config.ts` (поиск root по
  lockfile'ам на машине роя ронял build с ENOENT в `.next`).

## Критерии приёмки

- [x] e2e: Анна открывает `/requests/<номер заявки Ильи>` → 404; то же для
  API. **Частично**: ICS-фид, PDF справки и чат AI — поверхностей ещё нет
  (задачи DIG-2x…DIG-46); слой и `uniformNotFoundResponse()` для них готовы,
  изоляция этих поверхностей закрывается в их собственных задачах.
- [x] Unit-тесты на каждую функцию data-слоя с чужим studentId
  (`tests/data-isolation.test.ts`, 34 теста: запросы/оценки/уведомления/
  обращения/расписание/экзамены/студенты-факультета/контекст/аудит/404).
- [x] Правило ESLint падает при импорте `@prisma/client` вне `src/server/`
  (и для `@prisma/adapter-*`, и для сгенерированного клиента; в `src/server/`
  разрешено) — `tests/eslint-isolation-rule.test.ts`, 7 тестов.

## Non-goals

- **ICS-фид, PDF-справка, чат AI** — собственных поверхностей на ветке нет;
  их задачи обязаны идти через `src/server/data/*` и `uniformNotFoundResponse()`
  (агент security проверяет каждый PR).
- **Prisma-адаптер dataDb и модель AuditLog в schema.prisma** — физическая
  схема принадлежит DIG-9/DIG-10; отображение порта на схему (включая
  будущие `ServiceRequest.number @unique`, `AuditLog`, `Staff.faculty`)
  описано в delta-спеке и выполняется при интеграции.
- **Staff-экраны** — отдельная задача; здесь только слой с проверкой факультета.
