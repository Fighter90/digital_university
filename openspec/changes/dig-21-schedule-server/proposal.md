# Proposal: серверная часть расписания — день, неделя, месяц, изменения (DIG-21)

## Зачем

Экран «Расписание» (DIG-22, экранная задача) и кабинет сотрудника (задача про
изменение пар) нуждаются в серверных данных: пары группы за период с
преподавателем, аудиторией и статусом (обычная / перенос / отмена с прежней
аудиторией и временем), срезы «день / неделя / месяц / ближайший учебный
день», детали пары с личными заметками студента и механизм «сотрудник изменил
пару → все студенты группы получили уведомление». Прототип отвечает на
вопрос «а где данные для листания недель и бейджей изменений?»

## Что

- `src/lib/schedule-time.ts` — чистая арифметика времени в поясе
  `Europe/Moscow` на Intl (без новых зависимостей): настенные компоненты,
  `fromMoscowWallClock` (двупроходный алгоритм, офсет вычисляется), ISO с
  офсетом `+03:00` (`toMoscowIso`), границы дня/недели (понедельник)/месяца
  как полуинтервалы `[from, to)`, границы семестра (осень 1.09–25.01,
  весна 9.02–30.06, июль/август → будущая осень) и `pageMoscowWeek` —
  листание недель с обрезкой по семестру (страница целиком вне семестра →
  null).
- Порт данных (DIG-12) дополнен скоупленными методами:
  `listScheduleByGroupRange` (индекс `@@index([groupId, startsAt])` в схеме
  Prisma уже есть), `probeScheduleEventById`, `saveScheduleEventChange`,
  `listStudentsByGroup`, заметки (`findNoteByStudentAndEvent`,
  `probeNoteByEvent`, `saveNoteByStudent` upsert, `deleteNoteByStudent`);
  `NotificationRow`/append получили опциональный `link` (колонка уже была
  в схеме). In-memory адаптер реализует всё 1:1.
- `src/server/data/schedule.ts`:
  - `getSchedule(db, ctx, { from, to })` — пары группы студента за период,
    отсортированные по времени; статус и previousRoom/previousStartsAt
    доходят наружу;
  - `getDay` / `getToday` / `getWeek` / `getMonth` / `getNextStudyDay` —
    срезы в московском времени, неделя и месяц обрезаются по семестру;
  - `getEventDetails(db, ctx, id)` — детали + своя заметка; чужая группа,
    чужой id и сотрудник дают ОДИНАКОВЫЙ null (uniform 404), причина —
    только в AuditLog (OWNERSHIP_DENIED / NOT_FOUND / ROLE_MISMATCH);
  - заметки: `saveEventNote` (upsert, trim, ≤500 знаков, только своя
    группа пары), `deleteEventNote` (только свои);
  - `applyScheduleChange(db, ctx, …)` — только STAFF: фиксирует событие
    изменения на самой паре (status + previousRoom / previousStartsAt +
    changeNote; при смене времени длительность сохраняется, `date`
    переезжает на новый московский день) и рассылает уведомление
    kind=SCHEDULE всем студентам группы пары, уважая PUSH-матрицу каждого
    студента (DIG-19: выключил PUSH по расписанию — уведомления нет).
- Barrel `@/server/data` экспортирует новые функции и типы
  (`StudentNoteRow`, `NextStudyDayView`, `ScheduleEventDetails` и др.).

## Допущения (зафиксированы тестами)

- Учебный календарь прототипа вымышленный: осень 1.09–25.01, весна
  9.02–30.06; январь — хвост осени. SemesterBounds — источник для
  листания «в пределах семестра».
- Заметка к паре одна (уникальность (studentId, eventId) — как в схеме
  Prisma `StudentNote`); «изменить» = upsert текста с сохранением createdAt.
- Событие изменения пары не заводит новую таблицу — живёт на самой паре
  (status/previousRoom/previousStartsAt/changeNote), как в каноне DIG-9.
- Время наружу — ISO 8601 с офсетом (`toMoscowIso`); внутри слоя — Date.

## Отклонения от текста задачи (обоснованные)

- Подпись `getSchedule(ctx, …)` из задачи расширена до
  `getSchedule(db, ctx, …)` — конвенция слоя данных DIG-12 (порт
  инъецируется, тестируется без Next.js).
- Заметка задачи предлагала `date-fns-tz`/Temporal polyfill; выбран
  `Intl.DateTimeFormat` с `timeZone: 'Europe/Moscow'` — та же гарантия
  «не хранить локальное время без пояса» без новой зависимости (Temporal
  в стабильном Node ещё нет, polyfill тянуть ради одного пояса избыточно).
- Server actions заметок и экран недели — задачи DIG-22/DIG-24 (экранные);
  DIG-21 поставляет слой данных и его тесты.

## Вне скоупа

- Экран недели/месяца и листание в UI (DIG-22), карточка пары (DIG-24),
  кабинет сотрудника (DIG-44+), ICS-экспорт, реальные Push/Email-каналы.
