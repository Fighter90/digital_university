# Delta: schedule (DIG-21) — серверные данные расписания

## ADDED Requirements

### Requirement: Пары группы за период

Слой данных ДОЛЖЕН возвращать пары группы студента за полуинтервал
`[from, to)` (`getSchedule(db, ctx, { from, to })`): дисциплина, тип пары,
преподаватель, аудитория, статус (`SCHEDULED` / `ROOM_CHANGED` /
`TIME_CHANGED` / `CANCELLED`), для переносов — прежняя аудитория и время
(`previousRoom`, `previousStartsAt`) и причина (`changeNote`). Строки
ДОЛЖНЫ быть отсортированы по времени начала и содержать только пары группы
из контекста сессии; сотрудник (без группы) получает пустой список с
записью в аудите.

#### Scenario: перенос доходит до клиента

- **WHEN** студент запрашивает неделю, в которой пара перенесена
  (аудитория 214 → 305)
- **THEN** в ответе пара со статусом `ROOM_CHANGED`, `room = 305`,
  `previousRoom = 214` и `changeNote`.

#### Scenario: отмена видна в списке

- **WHEN** в периоде есть отменённая пара
- **THEN** она возвращается со статусом `CANCELLED` и своей заметкой
  (пары не выбрасываются из выборки).

#### Scenario: скоуп группы

- **WHEN** сотрудник вызывает `getSchedule` без группы
- **THEN** результат — пустой массив, в AuditLog добавлена запись
  `ROLE_MISMATCH`; пары чужой группы студент не получает ни при каком
  периоде.

### Requirement: Время в Europe/Moscow, наружу ISO

Все границы дня, недели (понедельник 00:00), месяца и семестра ДОЛЖНЫ
считаться в часовом поясе `Europe/Moscow`; наружу время ДОЛЖНО отдаваться
строкой ISO 8601 с офсетом пояса (`2026-11-11T10:00:00+03:00`,
`toMoscowIso`). Локальное «наивное» время без пояса не хранится и не
вычисляется.

#### Scenario: границы недели

- **WHEN** пара стоит в воскресенье 15 ноября 23:40 MSK, следующая — в
  понедельник 16 ноября 08:10 MSK
- **THEN** неделя 9–16 ноября содержит только воскресенскую пару, неделя
  16–23 ноября — только понедельничную.

#### Scenario: ISO с офсетом

- **WHEN** время пары преобразуется в строку для клиента
- **THEN** строка имеет вид `2026-11-11T12:00:00+03:00` (офсет присутствует).

### Requirement: Листание недель в пределах семестра

`pageMoscowWeek(date, delta, bounds)` ДОЛЖНА сдвигать неделю на `delta`
недель и обрезать интервал по границам текущего семестра (`semesterBounds`):
неделя целиком вне семестра — `null` (страницы нет, UI отключает листание),
частично пересекающаяся — обрезается. Срезы `getWeek` / `getMonth` ДОЛЖНЫ
использовать те же границы; `getDay` / `getToday` возвращают пары
московского календарного дня; `getNextStudyDay` — ближайший день с парами
после сегодня (пустые дни пропускаются, пар впереди — null).

#### Scenario: назад от начала семестра

- **WHEN** семестр начался 1 сентября (вторник) и студент листает неделю
  назад от первой недели
- **THEN** `pageMoscowWeek(…, -1)` возвращает `null`; первая страница
  обрезана до `1 сентября 00:00 – 7 сентября 00:00` MSK.

#### Scenario: вперед за конец семестра

- **WHEN** листание из последней недели семестра (18–24 января) на +1
- **THEN** `null`; неделя 25 января не существует.

#### Scenario: ближайший учебный день

- **WHEN** сегодня и завтра пар нет, послезавтра — одна пара
- **THEN** `getNextStudyDay` возвращает послезавтра (`dateKey`), одну пару
  и её список; пар впереди нет → `null`.

### Requirement: Детали пары защищены от IDOR

`getEventDetails(db, ctx, id)` ДОЛЖЕН возвращать детали пары и собственную
заметку студента только если пара относится к группе студента из контекста
сессии. Чужая группа, несуществующий id и сотрудник ДОЛЖНЫ получать
единообразный `null` (HTTP-эквивалент — uniform 404), причина отказа —
только в AuditLog (`OWNERSHIP_DENIED` / `NOT_FOUND` / `ROLE_MISMATCH`).

#### Scenario: чужая группа

- **WHEN** студент ПИ-21 запрашивает детали пары группы ЭК-11
- **THEN** `null`, в аудите `OWNERSHIP_DENIED`; ответ неотличим от ответа
  на несуществующий id (`NOT_FOUND`).

### Requirement: Заметки студента к паре — только свои

Студент ДОЛЖЕН уметь создать/изменить/удалить заметку к паре своей группы
(`saveEventNote` — upsert по паре студент+пара с trim и лимитом 500
знаков; `deleteEventNote`). Заметка к паре чужой группы запрещена (null +
аудит); сотрудник заметки не пишет; пустой и слишком длинный текст
отклоняется без записи. При изменении `createdAt` сохраняется.

#### Scenario: создать и изменить

- **WHEN** студент сохраняет заметку «Принести ноутбук», затем «Взять
  конспект»
- **THEN** детали пары возвращают одну заметку с новым текстом и прежним
  `createdAt`.

#### Scenario: чужая пара

- **WHEN** студент пытается создать или удалить заметку на паре чужой
  группы
- **THEN** `null` / `false` и запись в аудите `OWNERSHIP_DENIED`.

### Requirement: Изменение пары сотрудником → событие + уведомления группе

`applyScheduleChange(db, ctx, eventId, input)` ДОЛЖЕН быть доступен только
сотруднику (студент — null + аудит `ROLE_MISMATCH`, данные не меняются),
фиксировать событие изменения на самой паре — статус
`ROOM_CHANGED`/`TIME_CHANGED`/`CANCELLED`, прежние аудитория/время и
причину — и создавать уведомление (`kind=SCHEDULE`, ссылка `/schedule`)
ВСЕМ студентам группы пары. При смене времени длительность пары
сохраняется, календарная дата (`date`) переезжает на новый московский день.
Уведомление ДОЛЖНО уважать PUSH-матрицу настроек каждого студента (DIG-19):
отключил PUSH по расписанию — уведомления нет.

#### Scenario: перенос аудитории

- **WHEN** сотрудник меняет аудиторию пары «Программирование» (401 → 402)
  с причиной «Замена аудитории»
- **THEN** пара получает `ROOM_CHANGED`, `previousRoom = 401`,
  `changeNote`; каждый студент группы ПИ-21 с включённым PUSH получает
  уведомление «Пара перенесена» с текстом
  «Программирование (ПИ-21, 12:00): ауд. 401 → 402. Причина: Замена
  аудитории».

#### Scenario: перенос времени

- **WHEN** сотрудник переносит пару с 13 ноября 09:00 на 14 ноября 11:20
- **THEN** `previousStartsAt = 09:00`, `startsAt = 11:20`, `date` = 14
  ноября, `endsAt` сдвинут на тот же дельта-интервал (длительность
  сохранена); уведомление «Изменено время пары — было 09:00, стало 11:20».

#### Scenario: отмена

- **WHEN** сотрудник отменяет пару с причиной
- **THEN** статус `CANCELLED`, студенты группы получают «Пара отменена»
  с причиной.

#### Scenario: матрица каналов уважается

- **WHEN** один из студентов группы отключил PUSH по типу SCHEDULE
- **THEN** уведомление создаётся всем, кроме него.

### Requirement: Быстрый ответ недели

Ответ недели ДОЛЖЕН готовиться быстрее 100 мс на сидовых данных: выборка
за период ДОЛЖНА опираться на индекс расписания (`ScheduleEvent
@@index([groupId, startsAt])` в схеме Prisma; в памяти — фильтр по группе
и полуинтервалу startsAt с сортировкой).

#### Scenario: сетка семестра

- **WHEN** в хранилище ~700 пар (16 недель × 5 дней × 4 пары + шум чужой
  группы) и студент запрашивает неделю
- **THEN** среднее время ответа < 100 мс, возвращены ровно 20 пар своей
  группы за неделю.
