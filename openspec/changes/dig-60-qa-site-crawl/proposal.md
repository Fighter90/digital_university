# DIG-60 — QA: весь сайт рабочий и кликабельный — обход всех ссылок и кнопок

## Зачем

Перед дедлайном подачи нужен гарантированный факт: на проде
(<https://ostrovok.store>) нет ни одной мёртвой ссылки или кнопки, ни одного
«белого экрана». Проверки делаются кодом (e2e-краулер), а не ручным кликом, —
чтобы прогон повторялся перед каждым деплоем.

## Что делаем

1. **e2e-краулер** `e2e/prod-crawl.spec.ts` (Playwright, оба профиля:
   desktop-1440 и mobile-360):
   - гость: лендинг (CTA «Войти»), `/login` («Забыли пароль?»),
     `/forgot-password` («Назад ко входу»), контракт редиректа
     `/dashboard → /login?next=%2Fdashboard` для анонима;
   - студент (демо-креды): все 8 пунктов бокового меню (клик по каждому),
     5 вкладок таб-бара и 5 пунктов «Ещё» (mobile-360), 5 вкладок настроек
     (`?tab=`), успеваемость (сводка → ведомость → дисциплина → сессия →
     выписка PDF), заявки (список → деталь → справка PDF → публичная
     проверка подлинности), расписание (день/неделя/месяц + «Детали пары»),
     каталог сервисов (каждая карточка услуг → свой `href`, избранное);
   - на каждой странице: документ отвечает 200, есть `<main>` с текстом,
     плашка «Концепт для конкурса», в консоли нет ошибок, ни один ответ
     сети не ≥ 400 (кроме намеренно проверяемых 404);
   - каждая внутренняя ссылка (`a[href^="/"]`) на каждой посещённой странице
     дополнительно проверяется GET-запросом (редиректы следуются) — финал
     должен быть < 400;
   - обработка ошибок: для вошедшего пользователя неизвестная страница и
     чужой номер заявки — аккуратный 404 с UI (не белый экран).
2. **Отчёт** «страница → элемент → статус» пишется в
   `test-results/dig-60-crawl-report.json` — источник комментария в Linear.

## Non-goals

- Деструктивные кнопки настроек намеренно не нажимаются: смена пароля
  (зафейленный ввод считался бы попыткой входа), «Выйти»/отзыв сессий
  (рушит сессию краулера). Их кликабельность проверяется на
  видимость/enablement, поведение закреплено unit-тестами DIG-44/DIG-55.
- Внешние ссылки (GitHub-документация) фиксируются в отчёте, но не роняют
  прогон: сторонний сервис не входит в зону ответственности прототипа.
- Исправление продуктовых багов: если краулер что-то находит — это отдельные
  задачи, а не расширение этой.

## Риски

- Rate-limit входа (30 попыток/15 мин на IP): краулер входит один раз на
  воркер (общий контекст в serial-серии), а не на каждый тест.
- Прод-данные демо-сида могли измениться (нет заявки/пар): тесты на детали
  пары и заявку пропускаются с предупреждением, если поверхности пусты.
