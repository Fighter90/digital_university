# Proposal: публичная проверка подлинности справки по QR + PDF-шаблон справки (DIG-47)

## Зачем

В аудированном ЛК справки заказываются и ждут обработки, но проверить
подлинность выданного документа получателю (банк, военкомат, работодатель)
негде. DIG-27 уже печатает на выписке код проверки (160 бит, base32) и
оставил рамку «под QR» с пометкой, что сканируемый QR и страница
`/verify/<код>` — предмет DIG-47.

## Что

- **PDF-шаблон справки** `src/lib/certificate-pdf.ts`: шапка вымышленного
  вуза, номер, дата выдачи, ФИО, программа, курс, форма обучения,
  назначение, отметка «электронный документ», **сканируемый QR-код**
  со ссылкой на `/verify/<код>` и код проверки текстом. Кириллица —
  векторным шрифтом DIG-27 (переиспользуется без изменений).
- **QR-энкодер** `src/lib/pdf/qr.ts`: собственная минимальная реализация
  (byte mode, версии 1–6, уровень коррекции L, все 8 масок с оценкой
  штрафа) — зависимость в прототип не добавляется, вывод детерминирован.
- **Публичная страница** `/verify/[code]` (без входа): статус-карточка
  «Документ действителен» (зелёный) / «Документ не найден» /
  «Отозван» (красный); видны только тип документа, дата выдачи, ФИО
  частично («Смирнова А. В.») и статус — ни оценок, ни контактов, ни
  полного имени. Подсказка «Как проверить документ». Плашка
  «Концепт для конкурса».
- **Слой данных**: модель `CertificateRow` (порт + memory-адаптер),
  функции `verifyCertificateByCode` (публичное чтение по
  неугадываемому коду — единственное осознанное исключение из
  owner-scope, возвращает ТОЛЬКО публичное представление),
  `getOrCreateCertificateForRequest` (выдача справки владельцу заявки,
  idемпотентно — один код на заявку) и `revokeCertificateByCode`
  (отзыв ТОЛЬКО сотрудником своего факультета).
- **API**: `GET /api/requests/[number]/certificate` — владелец скачивает
  PDF готовой заявки-справки (единый 404 для чужих/несуществующих);
  `POST /api/staff/certificates/revoke` — сотрудник отзывает справку по
  коду (сразу меняет статус на странице проверки).
- **Rate limit перебора кодов**: скользящее окно по IP на странице
  `/verify/<код>` (пределы в `src/server/verify/rate-limit.ts`); при
  превышении — отдельное состояние «Слишком много попыток», без ответа
  об ошибке формата кода.
- Код проверки: 32 символа base32 (160 бит ≥ 128 бит приёмки),
  генерация через `crypto.getRandomValues`; страница принимает код и с
  дефисами, и без (нормализация).
- Сид: две демо-справки — действительная (Анна, для анонимной проверки
  жюри) и отозванная (Илья); справка заявки `req-anna-1` выдаётся
  лениво при первом открытии карточки заявки.

## Non-goals

- Выписка из зачётки (DIG-27) остаётся с кодом без QR: она мгновенная и
  не создаёт записи в реестре — проверять нечего. Вернёмся, если
  выписки станут отслеживаемыми документами.
- Prisma-модель `CertificateIssue` (канон DIG-9) и PostgreSQL-адаптер
  слоя данных не затрагиваются: прототип живёт на memory-адаптере, как
  и весь остальной кабинет; reconcile — отдельная задача (DIG-49 класс).
- UI кабинета сотрудника (отзыв из интерфейса) — DIG-48; сейчас отзыв
  доступен защищённому API-эндпоинту с проверкой роли и факультета.
- Истёкшая справка (`expiresAt` в прошлом) показывается как «не найден»:
  документ, вышедший из реестра, не подтверждается — отдельного статуса
  в договоре страницы нет.

## Риски

- QR-энкодер с нуля: закрыт round-trip-тестом (извлечение кодовых слов
  из матрицы, нулевые синдромы Рида–Соломона, разбор сегмента) и
  структурными проверками (finder/timing/format-info BCH).
- Публичная страница без входа: закрывается rate limit'ом, нормализацией
  входа, отсутствием ответов «формат неверный» и минимальным
  публичным представлением без PII.
