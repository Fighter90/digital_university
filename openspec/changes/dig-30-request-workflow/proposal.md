# DIG-30 — Заявки и справки: серверная логика и машина статусов

## Зачем

«Цифровой деканат» держится на прозрачности заявок: заказ документа онлайн,
понятный статус, конкретные уведомления. Сегодня в кабинете заявки только
читаются (сид DIG-10), заказать новую нельзя, статусы не переходят, номера —
случайные `SR-…` вместо каноничных «ЗД-ГГГГ-NNNNNN», словарь статусов TS-мира
(5 значений) расходится с каноническим enum Prisma (8 значений, решение
reconcile DIG-49: NEEDS_REVISION→NEEDS_FIX, COMPLETED→ISSUED).

## Что

- **Каталог типов заявок** (`RequestType`-словарь канона): 6 вымышленных типов
  с полями формы (JSON-описание + zod-валидация на сервере), SLA в рабочих
  днях, признаком «мгновенная» и построителем названия «тип · ключевой
  параметр» («Справка об обучении · для банка»).
- **Машина статусов** — чистый модуль: разрешённые переходы
  `SUBMITTED → ACCEPTED → IN_PROGRESS → READY → ISSUED`, ветки `NEEDS_FIX`
  (обязательная причина) → `SUBMITTED` после исправления, `REJECTED` (с
  причиной), `CANCELLED` (только студентом и только до `IN_PROGRESS`);
  проверка роли на каждый переход (студент не может перевести в READY и т.д.).
- **Номер «ЗД-<год>-<6 цифр>»**, уникальный (адаптер-хранилище выделяет
  следующий свободный за год; формат закреплён паттерном).
- **Серверный слой**: `submitRequest` (валидация полей, дедупликация «та же
  справка за 24 часа уже готова» → предлагает скачать готовую; мгновенные
  типы сразу READY с PDF), `transitionRequest` (переход + `RequestEvent`
  + уведомление с конкретикой: «Заявка ЗД-2026-000123 «Справка для
  военкомата»: Принята → В работе. Готовность до 14 ноября»).
- **SLA-дата готовности** по типу с пропуском выходных (сб/вс).
- **Мгновенные типы** («Справка об обучении», «Выписка оценок») сразу
  получают PDF: справка об обучении генерируется новым сборщиком PDF и
  отдаётся через `/api/requests/[number]/pdf` (скоуп владельца, единый 404);
  выписка оценок переиспользует мгновенный `/api/grades/transcript` (DIG-27).
- **Словарь статусов TS-мира → канонический (8 значений)**: сиды и
  дашборд переводятся на NEEDS_FIX/ISSUED, бейджи получают 8 статусов.
- **Server actions** (`src/server/actions/requests.ts`) для будущего экрана
  подачи заявки: подать / отменить / отправить исправленную.

## Не делаем (вне задачи)

- Экран подачи заявки и кабинет сотрудника по заявкам (отдельные задачи);
  серверная логика и API готовы к ним.
- Сканируемый QR в PDF (DIG-47) — печатается код проверки и рамка.
- Prisma-адаптер данных: прототип работает на in-memory адаптере (DIG-12),
  контракт порта расширяется совместимо.

## Риски

- Смена словаря статусов затрагивает сиды, дашборд и 3 тестовых файла —
  правки механические (COMPLETED→ISSUED, NEEDS_REVISION→NEEDS_FIX),
  поведение «в работе» сохраняется (SUBMITTED/ACCEPTED/IN_PROGRESS/NEEDS_FIX).
- Последовательные номера «ЗД-…» перечислимы — защита IDOR остаётся в
  скоупе владельца + единый 404 (как и для канонической модели Request).
